# OAuth 보안 핫픽스 설계

## 배경

PR #42 병합 후 다음 세 가지 리뷰 지적을 별도 핫픽스로 처리한다.

1. 공급자가 전달한 이메일이 기존 Snowthing 회원과 같다는 이유만으로 소셜 계정을 자동 연결하면 계정 탈취로 이어질 수 있다.
2. 네이버 프로필 응답에 이메일이 존재하는 사실은 해당 이메일의 현재 소유권을 네이버가 보증한다는 뜻이 아니다.
3. 세션에 OAuth `state` 하나만 저장하면 여러 탭에서 시작한 로그인 요청이 서로 덮어쓰고, 잘못된 콜백이 정상 요청까지 삭제한다.

## 결정

### 계정 식별과 이메일 신뢰를 분리한다

- 이미 연결된 계정은 `(provider, providerUserId)`로만 식별해 로그인한다.
- 연결되지 않은 소셜 계정의 권위 있는 이메일이 기존 회원 이메일과 일치하면 자동 연결하지 않고 `OAUTH_ACCOUNT_LINK_REQUIRED`로 거절한다. 비권위 이메일은 기존 회원 조회에 사용하지 않는다.
- 일치하는 기존 회원이 없으면 추가 이메일 인증 없이 신규 소셜 회원을 생성한다.
- 네이버 이메일은 프로필 정보로만 저장하고 Snowthing 이메일 인증 완료로 표시하지 않는다.
- 구글은 `email_verified=true`이면서 Gmail 주소이거나 Workspace `hd` 클레임이 있을 때만 Snowthing 이메일 인증 완료로 표시한다.
- 이메일 신뢰 여부가 낮더라도 신규 소셜 계정 생성과 이후 `(provider, providerUserId)` 로그인은 허용한다. 신뢰 여부는 기존 계정 연결 권한으로 사용하지 않는다.
- 비권위 이메일은 `Member.email`을 점유하지 않는다. `Member.email`에는 `(provider, providerUserId)`를 SHA-256으로 해시한 `oauth-{provider}-{digest}@users.invalid` 내부 식별자를 저장하고, 실제 제공자 이메일은 `MemberSocialAccount.providerEmail`에만 보관한다.

이 방식은 소셜 가입 직후 별도 이메일 인증을 요구하지 않으면서, 이메일 문자열만으로 기존 계정 권한을 얻는 경로를 제거한다.

### 여러 OAuth 요청을 독립적으로 보관한다

- 세션에는 최대 5개의 대기 중 OAuth 요청을 불변 목록으로 저장한다.
- 각 요청은 공급자, 난수 `state`, 안전하게 정제된 `returnUrl`, 10분 만료 시각을 가진다.
- 인가 시작 시 만료 항목을 정리하고 새 요청을 추가한다. 한도를 넘으면 가장 오래된 요청을 제거한다.
- 콜백은 일정 시간 비교로 일치하는 `state`를 찾고, 일치한 요청만 한 번 소비한다.
- 알 수 없는 `state`는 다른 정상 요청을 제거하지 않는다.
- 같은 `state`가 다른 공급자 콜백으로 들어오면 실패하되 원래 요청은 보존한다. 정상 공급자 콜백이 일치한 요청만 소비한다.

## 계층 책임

- `OAuth2ExternalClient`: 공급자 응답을 표준 프로필로 변환하고 이메일 신뢰 수준을 계산한다.
- `SocialAuthService`: 공급자 고유 ID 조회, 이메일 충돌 거절, 신규 회원 및 연결 레코드 생성을 담당한다. 웹 세션을 다루지 않는다.
- `OAuth2AuthController`: 대기 중 `state` 목록, 콜백 소비, 인증 세션 발급을 담당한다.
- 프런트엔드 로그인 화면: `OAUTH_ACCOUNT_LINK_REQUIRED` 안내를 표시한다.

## 데이터와 API 영향

- 데이터베이스 스키마 변경은 없다.
- 기존 OAuth 엔드포인트와 정상 리다이렉트 계약은 유지한다.
- 오류 코드 `AUTH_012 / OAUTH_ACCOUNT_LINK_REQUIRED`를 추가한다.
- 이미 잘못 자동 연결된 과거 데이터는 이 핫픽스에서 자동 분리하지 않는다. 공급자 ID와 회원 소유권을 별도로 확인하지 않고 일괄 분리하면 정상 연결을 끊을 수 있기 때문이다.

## 테스트 계획

- 미연결 소셜 계정의 권위 있는 이메일이 기존 회원과 같으면 회원·소셜 연결을 생성하지 않는다.
- 신규 네이버 회원은 생성되지만 `emailVerifiedAt`은 비어 있다.
- 신규 네이버·구글 외부 도메인 회원의 제공자 이메일은 `Member.email`을 점유하지 않고 내부 식별 이메일과 분리된다.
- Gmail 및 Workspace 구글 회원만 로컬 이메일 인증 시각이 기록된다.
- 이미 연결된 소셜 계정은 프로필 이메일 신뢰 여부와 무관하게 로그인된다.
- 두 탭에서 만든 두 `state`가 역순으로 각각 성공한다.
- 변조된 콜백이 다른 정상 `state`를 삭제하지 않는다.
- 다른 공급자 콜백이 원래 공급자의 정상 `state`를 소비하지 않는다.
- 소비된 `state` 재사용, 만료 요청, 공급자 불일치를 거절한다.
- 세션의 대기 요청은 최대 5개로 제한된다.

## 구현 순서

1. 실패하는 서비스·외부 클라이언트·컨트롤러 테스트를 먼저 추가한다.
2. 이메일 신뢰 판정과 자동 연결 차단을 구현한다.
3. 다중 `state` 저장·소비 구조를 구현한다.
4. 로그인 오류 안내와 소셜 로그인 설계 문서를 갱신한다.
5. 백엔드 전체 테스트·Spotless, 프런트엔드 lint/build, diff 검사를 수행한다.
6. `docs/project/work.md`에 완료 범위와 남은 계정 연결 UI 작업을 기록한다.
