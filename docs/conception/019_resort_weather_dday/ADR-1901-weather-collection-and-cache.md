# ADR-1901 리조트 기온 수집·캐시 방식

- 상태: Accepted
- 결정일: 2026-11-04

## 문제

슬로프캠 헤더에 리조트 기온을 보여 주려면 외부 데이터를 가져와야 한다. 운영 서버는 단일 EC2라서 자원 여유가 적다. 외부 사이트가 느리거나 죽어도 캠 페이지에 영향이 가면 안 되고, 보는 사람이 없을 때는 호출이 생기지 않아야 한다. 나중에 서버를 늘리고 Redis 공유 캐시로 옮길 수 있어야 한다.

이 문제는 세 가지 결정으로 나뉜다.

1. 데이터를 어디서 가져올 것인가
2. 언제, 어떻게 수집하고 캐시할 것인가
3. 프론트가 어떻게 받을 것인가

## 1. 데이터 소스

### 후보

1. 기상청 초단기실황으로 통일: 소스 하나, 관측 실황, 무료. 5km 격자라 슬로프 위치값은 아니다.
2. 공식 사이트 크롤링 우선 + 기상청 대체: 리조트가 직접 보여 주는 값과 같다. 파서 여러 종을 유지해야 한다.
3. 고도 보정 예보 API(Open-Meteo): 위경도와 고도로 정상·베이스 추정값을 준다. 실측이 아닌 모델값이고 해외 서비스에 의존한다.
4. 해외 상용 스키 API(OnTheSnow, weather.com): 유료 파트너 계약이 필요하고, 국내 리조트 커버리지가 확인되지 않는다.

### 결정

2번. 리조트 홈페이지와 같은 값을 보여 주는 쪽을 택했다.

### 대가

- 조사해 보니 공식 값도 대부분 웨더아이나 기상청의 지역 값이다. 정확도는 1번과 크게 다르지 않다.
- 사이트 개편 때 파서가 깨진다. 실패하면 기상청으로 자동 대체되게 해서 사용자에게는 출처만 바뀌어 보이게 한다.
- 정상/베이스 구분은 어느 후보도 실측으로 주지 않는다. 범위에서 제외했다.

## 2. 수집 시점과 캐시

### 후보

| 후보 | 방식 | 응답 속도 | 하루 외부 호출 | 장애 시 | 구현 |
|---|---|---|---|---|---|
| A. 요청 시 + 만료 캐시 | 10분이 지나면 다음 요청이 직접 수집 | 10분마다 첫 요청 0.3~1초 | 보는 만큼 (0~1,872) | 칩 사라짐 | 가장 단순 |
| B. 요청 시 + 미리 갱신 | 8분 후 첫 요청은 기존 값을 받고, 뒤에서 수집 | 거의 즉시 | 보는 만큼 | 30분까지 직전 값 | 중간 |
| C. 스케줄러 전체 수집 | 10분마다 13곳 수집 | 항상 즉시 | 1,872 고정 | 직전 값 | 낮음~중간 |
| D. 스케줄러 + 시간·시즌 제한 | C를 운영 시간에만 | 운영 시간엔 즉시 | 약 800 | 직전 값 | 중간 |
| E. Redis 공유 캐시 | A·B의 저장소를 Redis로 | A·B와 같음 | A·B와 같음 | A·B와 같음 | 중간~높음 |
| F. Next.js 서버에서 수집 | `fetch` `revalidate`로 SWR | 거의 즉시 | 보는 만큼 | 직전 값 | 낮음 |
| G. HTTP 캐시 헤더 | `Cache-Control` 로 브라우저·CDN 캐시 | 재요청만 빨라짐 | - | - | 낮음 (보조) |
| H. 브라우저 직접 호출 | 휘닉스·오크밸리 방식 | - | - | - | 키 노출, CORS로 불가 |

### 결정

B를 채택하고 G를 보조로 쓴다. 저장소와 갱신 조정을 인터페이스로 분리해 E로 옮길 수 있게 만든다.

### 근거

- 작은 서버에서는 "보는 사람이 있을 때만 호출"이 가장 중요하다. C·D는 아무도 안 봐도 호출한다.
- B는 응답 속도와 장애 대응이 C 수준이고, 호출량은 A 수준이다.
- E는 지금 서버가 1대라 얻는 것이 없다. 대신 전환 비용이 작도록 경계를 미리 나눈다.
- F는 SWR을 공짜로 얻지만, 크롤링과 서비스 키가 프론트 서버로 가고 Jsoup 기반 구현과 맞지 않는다. 프론트 서버 자원을 대신 쓰는 것이라 전체 부담은 같다.

### 대가와 대응

- 값이 최대 몇 분 오래될 수 있다. 관측 시각을 화면에 보여 주고, 30분 상한을 넘으면 버린다.
- 백그라운드 갱신이 JVM 공용 풀을 쓰면 다른 작업을 밀어낸다. 스레드 2개짜리 전용 풀을 쓰고, 큐가 차면 갱신을 건너뛴다.
- 오래 아무도 안 본 리조트는 만료되어 다음 첫 요청이 느리다(A와 같다). 비시즌·새벽에는 자원을 쓰지 않는 쪽을 택했다.
- 비동기 갱신이라 테스트가 어렵다. `Clock`과 실행기를 주입해 동기로 검증한다.

### Caffeine `refreshAfterWrite`를 쓰지 않는 이유

- B는 Caffeine `LoadingCache`의 `refreshAfterWrite`로 가장 짧게 구현할 수 있다.
- 하지만 그렇게 하면 "8분 후 갱신, 30분 후 만료, 동시 수집 1회" 정책이 Caffeine 안에 숨는다. Redis로 옮길 때 이 정책을 처음부터 다시 짜야 한다.
- 그래서 정책은 서비스가 `fetchedAt`으로 직접 판단하고, Caffeine은 만료만 하는 단순 저장소로 쓴다.
- 지금 코드가 조금 늘어나는 대신, Redis 전환 때는 저장소와 조정자 구현체만 추가한다.

## 3. 프론트 전달

### 후보

1. 별도 API `GET /api/v1/resort-cams/{code}/weather`를 브라우저에서 호출
2. 기존 리조트 목록 API에 포함

### 결정

1번.

### 근거

- 캠 페이지는 서버에서 목록 API를 1.5초 타임아웃으로 받고, 실패하면 폴백 데이터를 쓴다. 기온 수집 지연이 여기에 섞이면 카메라 목록까지 폴백으로 떨어질 수 있다.
- 기온은 실패해도 칩만 숨기면 된다. 영상과 독립적으로 실패하게 분리한다.
- 대가: 페이지당 요청이 1개 늘어난다. 캐시 헤더와 서버 캐시로 비용은 무시할 수준이다.

## 4. 개장일 (참고)

- 후보: DB 컬럼 + 마이그레이션, DB + 관리자 화면, 프론트 상수, 공식 홈페이지 크롤링.
- 결정: 프론트 상수. 개장일은 시즌에 한 번 바뀌는 13개 값이고, 공개 API가 없다. 배너도 시즌 시작 후 내릴 임시 기능이다.
- 대가: 날짜를 바꿀 때마다 배포가 필요하다. 시즌당 몇 번이라 감수한다.
