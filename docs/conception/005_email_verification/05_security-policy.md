# 이메일 인증 보안·만료·제한 정책

## 1. 인증번호와 토큰

- 인증번호는 `SecureRandom`으로 000000~999999 범위에서 생성합니다.
- 인증번호는 6자리 문자열로 취급해 앞자리 0을 보존합니다.
- DB에는 서버 비밀값 기반 HMAC-SHA256만 저장합니다.
- HMAC 입력에 요청 UUID, 정규화 이메일, 용도와 인증번호를 함께 넣습니다.
- 비교는 상수 시간 비교를 사용합니다.
- 인증 완료 토큰은 32바이트 이상 난수를 Base64 URL-safe 문자열로 인코딩합니다.
- 토큰 원문은 한 번만 반환하고 DB에는 HMAC만 저장합니다.

## 2. 만료와 재사용

- 번호 유효시간: 5분
- 가입·재설정 토큰 유효시간: 15분
- 재발송 대기: 60초
- 인증 실패: 최대 5회
- 새 번호 발송: 이전 번호와 요청 UUID 폐기
- 가입·비밀번호 변경: 토큰을 같은 트랜잭션에서 소비

## 3. 호출 제한

- 이메일별 시간당 5회: MySQL 상태로 유지
- IP별 시간당 20회: 현재 단일 인스턴스에서는 Caffeine 사용
- IP 제한은 서버 재시작 시 초기화되며 다중 인스턴스 전환 시 Redis로 교체
- 가입 중복 확인 API는 발송 제한과 별도로 IP별 슬라이딩 60초 동안 10회까지 허용
- 중복 확인 제한 초과 시 회원 조회를 실행하지 않고 `429 EMAIL_010` 반환
- 제한 초과 시 SES를 호출하지 않음

## 4. 계정 열거 방지

- 회원가입 중복 확인은 기능 특성상 이메일 존재 여부를 반환합니다.
- 비밀번호 재설정은 계정 존재 여부와 관계없이 같은 HTTP 상태와 본문을 반환합니다.
- 존재하지 않는 이메일에도 형식상 `requestId`를 반환합니다.
- 최소 응답 시간과 작은 무작위 지연으로 단순 시간 비교를 어렵게 합니다.
- 존재하는 계정의 이메일별 발송 제한 또는 SES 장애도 외부에는 동일한 `202` 응답으로 숨기고 내부 경고 로그로만 남깁니다. IP 전체 제한은 남용 차단을 위해 `429`를 반환합니다.
- 로그와 메트릭 태그에 전체 이메일을 사용하지 않습니다.

## 5. 세션 폐기

- 로그인 성공 시 보안 계층이 회원별 세션을 등록합니다.
- 비밀번호 변경 커밋 후 보안 계층이 해당 회원의 세션을 모두 만료시킵니다.
- 라이브톡 연결 레지스트리와 세션 폐기 레지스트리에도 같은 세션 ID를 전달합니다.
- 세션 조작은 Controller·Security 계층에서만 수행합니다.
- 단일 서버 세션 구조를 Redis로 이전할 때 회원별 세션 인덱스도 공용 저장소로 옮깁니다.

## 6. 로그와 개인정보

- 금지: 인증번호, 토큰, 전체 이메일, SES 원문 본문
- 허용: 내부 요청 UUID, SES messageId, 목적, 결과 코드, 처리 시간
- 운영 로그에서 이메일 식별이 필요하면 서버 비밀값으로 만든 짧은 이메일 HMAC만 사용합니다.
- 종료 상태 인증 행은 24시간 후 삭제합니다.

## 7. 트레이드오프

동기 SES 호출은 구현과 장애 판단이 단순하지만 응답 지연과 DB 저장 후 발송 실패 사이의 간극이 있습니다. 발송 실패 행을 명시적으로 남기고 사용자가 다시 요청할 수 있게 하여 복구합니다. 메일 한 건의 유실도 허용할 수 없거나 발송량이 커지면 Transactional Outbox와 비동기 작업자를 재검토합니다.

SES 배달 이벤트를 애플리케이션 상태에 반영하지 않으므로 Inbox는 사용하지 않습니다. 사용자가 인증번호를 성공적으로 제출한 시점을 서비스 수준의 수신 확인으로 봅니다.

중복 확인 제한은 Caffeine 기반 단일 인스턴스 정책이므로 서버 재시작 시 초기화되고, 여러 사용자가 같은 공인 IP를 쓰는 NAT 환경에서는 정상 요청도 함께 제한될 수 있습니다. 다중 인스턴스 전환 시 Redis 기반 공용 슬라이딩 윈도우로 교체하고, 운영의 `EMAIL_010` 발생률을 기준으로 한도를 재조정합니다. 분산 IP를 사용하는 봇은 애플리케이션 IP 제한만으로 막을 수 없으므로 공격 규모가 커지면 WAF 또는 봇 탐지를 함께 적용합니다.
