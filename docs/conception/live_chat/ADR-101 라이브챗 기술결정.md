# ADR-101 라이브챗 아키텍처 및 컴플라이언스 의사결정

- 상태: Accepted
- 결정일: 2026-09-19
- 대상: `com.ikae.snowthing.domain.chat`, `com.ikae.snowthing.global.config.websocket`
- 인프라 환경: AWS EC2 1대 (2GB RAM, 2GB Swap), RDS MySQL 8.0 1대, S3 1개, ECR 2개, CloudFront 1개, 호스트 Nginx 리버스 프록시

---

## 1. 문제 정의

현재 Snowthing의 게시판과 향후 도입될 매칭 기능은 비실시간 요청-응답 모델로 동작한다. 이 방식은 사전 일정 조율에는 적합하지만 다음과 같은 실시간 요구를 처리하지 못한다.

1. **당일 동행 구인**: "오늘 지금 탈 사람", "1시간 뒤 리프트 같이 탈 사람"처럼 당장 필요한 소통을 지원하지 못한다.
2. **장비 급처**: 스키장 현장에서 당일 빠르게 직거래하고 싶을 때 실시간으로 대화할 수단이 없다.
3. **슬로프 현황 공유**: 공식 웹캠보다 빠른 빙판 상태, 리프트 대기 시간 등을 현장에 있는 사람들끼리 바로 묻고 답하기 어렵다.
4. **접속자 유입 및 유지**: 사용자가 사이트를 켜두고 실시간으로 소통할 수 있는 창구가 없다.

---

## 2. 컴플라이언스 및 법적 운영 정책

실시간 채팅은 불법 정보 유통 및 범죄 악용 가능성이 존재하므로 기술 선택 전에 법적 방어 기준을 정의한다.

### 2.1. 방조죄 및 불법정보 차단
- 사용자가 마약 거래, 도박 사이트, 음란물을 유포할 경우 직접 행위자가 1차 처벌 대상이지만, 운영자가 이를 인지하고도 방치하거나 기술적 차단 조치를 취하지 않으면 형법 제32조(방조죄) 및 정보통신망법 제44조의7 위반 책임이 발생한다.
- **회원 전용(Member-Only) 강제**: 비회원 익명 접근을 차단하여 스팸 매크로와 악성 유저 유입을 억제하고 회원가입을 유도한다.
- **외부 링크 및 메신저 ID 정규식 차단**: 불법 거래 유도의 핵심 통로인 URL(`http://`, `https://`, `.com` 등)과 텔레그램/오픈카톡 식별자(`t.me/`, `@` 등)를 메시지 전송 인터셉터에서 차단한다.
- **비상 셧다운 스위치(Kill Switch)**: 관리자 기능과 함께 후속 구현한다. 현재 단계에는 포함하지 않는다.

### 2.2. 대화 본문 미저장과 접속 로그 보관 의무
- **대화 본문 미저장**: 대화 텍스트는 DB에 저장하지 않고 인메모리 휘발성으로 운영한다. 최근 30개는 같은 서버가 살아 있는 동안 새로고침 시 복원되지만 재시작·재배포하면 사라진다.
- **통신사실확인자료 보관 (통신비밀보호법 제15조의2, 시행령 제41조)**: 수사기관 영장 집행 대응을 위해 `member_id`, `client_ip`, `room_id`, `timestamp` 메타데이터만 별도 텍스트 로그로 기록하고 최소 3개월(90일) 보관 후 자동 파기한다.

## 3. 검토 후보군 및 비교

현재 단일 EC2(2GB RAM)와 Nginx + CloudFront 프록시 구성을 기준으로 5개 후보를 검토했다.

| 항목 | 후보 1: STOMP (SimpleBroker) | 후보 2: Raw WebSocket | 후보 3: SSE + POST | 후보 4: STOMP + Redis Pub/Sub | 후보 5: 외부 SaaS (Pusher 등) |
|---|---|---|---|---|---|
| 추가 인프라 비용 | 0원 | 0원 | 0원 | 월 $15 이상 (ElastiCache) | 종속 과금 |
| EC2 메모리 부하 | 낮음 (JVM 내장) | 낮음 | 보통 | 높음 (로컬 구동 시 OOM 위험) | 없음 |
| 프로토콜 | 전이중 양방향 | 전이중 양방향 | 반이중 (수신 SSE / 발신 POST) | 전이중 양방향 | 전이중 양방향 |
| 구현 복잡도 | 낮음 (어노테이션 기반) | 높음 (세션·방 직접 구현) | 보통 (채널 이원화) | 보통 | 매우 낮음 |
| 컴플라이언스 통제 | 자체 통제 가능 | 자체 통제 가능 | 자체 통제 가능 | 자체 통제 가능 | 불가 (서드파티 종속) |
| 스케일아웃 확장성 | 설정 교체로 확장 가능 | 재개발 필요 | 재개발 필요 | 즉시 확장 가능 | 무제한 |

### 기각 사유
- **후보 2 (Raw WebSocket via `TextWebSocketHandler`)**: STOMP 헤더를 줄이기 위해 세션 컬렉션 관리, 방별 매핑, JSON 파싱을 직접 구현하는 것은 바퀴의 재발명이다. 세션 비정상 종료 시 동기화 오류 및 메모리 누수 위험이 크다.
- **후보 3 (SSE + HTTP POST)**: 브라우저당 도메인별 HTTP 연결 수 한계가 존재하고, 수신과 발신 채널이 쪼개져 세션 추적 복잡도만 증가한다.
- **후보 4 (STOMP + Redis Pub/Sub)**: 단일 EC2 환경에서 AWS ElastiCache를 추가하는 것은 불필요한 비용 지출이며, EC2 내부에 Redis를 띄우면 2GB 메모리 환경에서 OOM 크래시를 유발한다.
- **후보 5 (외부 SaaS)**: 트래픽 종속 비용이 발생하고 외부 링크 차단 및 감사 로그 통제가 불가능하다.

---

## 4. 결정

**후보 1: Spring WebSocket + STOMP (인메모리 SimpleBroker)를 채택한다.**

### 결정 이유
1. **비용 및 자원 적합성**: 현재 단일 EC2(2GB RAM) 환경에서 추가 인프라 비용 없이 안정적으로 구동된다.
2. **KISS 원칙 준수**: 단일 서버 환경에서 불필요한 외부 브로커를 배제하고 가장 간결한 구조를 유지한다.
3. **스프링 생태계 통합**: `@MessageMapping`을 통해 인증, 입력 검증, 도배·링크 차단과 감사 로그를 일관되게 처리할 수 있다. DB 기반 금칙어는 관리자 기능에서 후속 구현한다.
4. **미래 확장성 보장**: 비즈니스 로직과 프론트엔드가 STOMP 규약에 의존하므로, 다중 서버 확장 시 비즈니스 코드 수정 없이 브로커 설정만 교체할 수 있다.

## 5. 스케일아웃(수평 확장) 전략

향후 EC2가 2대 이상으로 확장되면 다음과 같이 진화한다.

1. **프론트엔드 및 컨트롤러 코드 변경 0건**:
   - `/sub/chat/main` 구독 및 `/pub/chat/messages` 발행 경로는 그대로 유지된다.
2. **Redis Pub/Sub 브로커 전환**:
   - `WebSocketConfig`에서 인메모리 `SimpleBroker` 대신 `RedisMessageListenerContainer`와 `RedisTemplate`을 이용한 브로커 릴레이로 전환하여 서버 간 메시지 브로드캐스팅을 수행한다.

## 6. 인프라 명세 및 트레이드오프

### 6.1. 프록시 설정
- **호스트 Nginx**:
  ```nginx
  location /ws-chat/ {
      proxy_pass http://127.0.0.1:8080;
      proxy_http_version 1.1;
      proxy_set_header Upgrade $http_upgrade;
      proxy_set_header Connection "Upgrade";
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_read_timeout 3600s;
      proxy_send_timeout 3600s;
  }
  ```
- **CloudFront**: `ws-chat/*` 경로에 대해 CachingDisabled 적용 및 `Upgrade`, `Connection`, `Host` 헤더 Forwarding 허용.

### 6.2. 트레이드오프 및 대응
- **유휴 연결 끊김**: Nginx 기본 60초 타임아웃을 3600초로 연장하고, STOMP 10초 Heartbeat(PING/PONG)를 활성화해 연결을 유지한다.
- **대화 내역 휘발**: 같은 서버에서는 최근 30개를 복원하지만 서버 재시작·재배포 시 사라진다. UI에 실시간 대화임을 명시한다.
- **감사 로그**: 본문을 제외한 메타데이터를 별도 파일로 기록하고 EC2 호스트에 보존한다. CloudWatch 전송, 접근 통제와 실제 보존 기간은 운영 설정과 법률 검토를 거쳐 확정한다.
- **로그아웃 후 기존 연결**: HTTP 로그아웃 시 세션 ID를 로컬 Caffeine 폐기 목록에 기록하고 STOMP `SEND`마다 검사한다. 단일 서버에서는 즉시 차단되지만 다중 서버에서는 로컬 상태가 공유되지 않으므로 Redis 전환이 필수다.
- **재연결 폭주**: 클라이언트의 지수 백오프와 지터, 서버 채널 실행기·큐·메시지 크기·전송 시간 상한으로 장애 시 자원 사용을 제한한다.
- **연결 상한**: 단일 회원은 마지막 연결 1개만 유지하고 서버 전체는 환경변수 기준 기본 500개로 제한한다. 로그아웃 시 연결을 즉시 종료하며 비정상 종료 이벤트에서도 등록을 제거한다.
- **IP 제한**: EC2 보안 그룹에서 80·443의 출처를 고객 관리형 `cloudflare-ipv4` 접두사 목록으로 제한한 뒤 Nginx가 공식 Cloudflare IPv4 대역에서 온 `CF-Connecting-IP`만 신뢰한다. 복원된 사용자 IP 기준으로 `/ws-chat` 동시 연결 5개와 초당 연결 시도 3개를 제한한다.
- **운영 대가**: Cloudflare가 공식 IP 대역을 변경하면 AWS 접두사 목록과 Nginx trusted proxy 목록을 함께 갱신해야 한다. 둘이 어긋나면 정상 요청 차단 또는 실제 IP 복원 실패가 발생하므로 배포 전 목록 비교가 필요하다.

### 단계별 로컬 부하 검증

`ChatLoadTest`는 일반 CI에서 제외되는 `benchmark` 태그로 관리한다. `-PchatLoadStage` 값으로 같은 코드와 측정 방식에서 접속자 수와 발송 라운드만 바꾼다. 모든 회원이 연결·구독을 마친 뒤 시작 장벽으로 한 라운드의 발송 시점을 맞춘다. N명이 메시지를 한 건씩 보내면 각 메시지가 N명에게 전달되므로 예상 수신량은 `N × N × 라운드 수`다.

2026-09-20 로컬 JVM에서 다음 순서로 실행했다.

| 단계 | 사용자 | 라운드 | 예상/실제 수신 | 연결 p95 | 수신 p95 | 수신 p99 | 최대 힙 | 최대 CPU | 오류 | 결과 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| baseline | 100 | 1 | 10,000 / 10,000 | 242ms | 359ms | 370ms | 143MB | 41.9% | 0 | 통과 |
| target | 200 | 1 | 40,000 / 40,000 | 358ms | 1,008ms | 1,031ms | 257MB | 59.2% | 0 | 통과 |
| high | 300 | 1 | 90,000 / 90,000 | 332ms | 2,115ms | 2,167ms | 247MB | 66.5% | 0 | 통과 |
| sustained | 200 | 5 | 200,000 / 200,000 | 334ms | 951ms | 1,081ms | 309MB | 61.9% | 0 | 통과 |
| extreme | 400 | 1 | 160,000 / 160,000 | 429ms | 4,517ms | 4,606ms | 338MB | 71.0% | 0 | 통과 |

현재 목표선은 200명이다. target과 sustained에서 손실·연결 종료·transport error가 없었고 수신 p95가 약 1초였다. 300명부터 p95가 2초를 넘고 400명에서는 4.5초까지 증가하므로, 데이터 유실 없이 끝났다는 이유만으로 300~400명을 서비스 가능 용량으로 판단하지 않는다. 300명 이상을 목표로 바꾸기 전에는 외부 부하 발생기와 운영 유사 EC2에서 다시 측정하고 SimpleBroker 대체, Redis 브로커 연계 또는 서버 확장을 재검토한다.

이 수치는 테스트 서버와 부하 발생기가 같은 JVM·장비의 CPU와 메모리를 함께 사용한 결과라 EC2 용량 보장이 아니다. 로그인 200건을 완전히 동시에 준비했을 때는 WebSocket 측정 전 Tomcat 접속 단계에서 `ConnectException`이 발생했으므로, 본 실험은 로그인 동시성을 20으로 제한해 채팅 연결과 fan-out을 분리해서 측정했다. 대규모 동시 로그인·재접속 폭주는 별도 시나리오로 검증해야 한다.
