# 📄 [Architecture Decision Record] Sprint 1 Day 2 세션 기반 인증 & N:M 설계 변경 명세서

> **본 문서는 Sprint 1 Day 2 세션 인증 및 데이터 모델링 설계 중 발생한 주요 변경 사항과 물리적 원리, 장단점(Trade-off), 극복 방안을 명확히 서술한 아키텍처 의사결정 문서입니다.**

## 1. 아키텍처 변경점 1: 다중 디바이스 동시 로그인 허용 (UX 우선 정책)

### 📌 변경 전 (Initial Design)
* 단일 계정당 단 1개의 활성 세션만 허용 (`maximumSessions(1)`). 
* 다른 기기에서 로그인 시 기존 세션을 즉시 강제 종료.

### 🔄 변경 후 (Current Architecture)
* **다중 디바이스 동시 로그인 전면 허용**: 유저가 PC, 스마트폰, 태블릿 등 여러 기기에서 동시 접속하더라도 세션을 유지시킴.

### 💡 물리적 원리, Trade-off 및 극복 방안
1. **물리적 원리**:
   * 각 기기 접속 시 톰캣 및 스프링 세션 레벨에서 각각 암호학적 난수로 생성된 독립적인 `JSESSIONID` 세션 객체를 생성하여 인메모리 세션 map 에 보관합니다.
2. **치러야 하는 대가 (Trade-off)**:
   * 동시 접속 기기가 무제한으로 늘어날 경우 서버 메모리(RAM)에 누적되는 세션 데이터량이 증가할 위험이 존재합니다.
3. **서비스/아키텍처 레벨 극복 방안**:
   * **`server.servlet.session.timeout=30m` 30분 세션 타임아웃**을 엄격히 적용. 
   * 유저가 브라우저를 닫거나 30분간 활동이 없을 경우 톰캣 백그라운드 `SessionCleaner` 스레드가 만료 세션 객체를 즉시 GC 메모리 회수하여 RAM 고갈을 방지함.

## 2. 아키텍처 변경점 2: 비밀번호 복잡도 2중 정규식 검증 도입

### 📌 변경 전
* 8자 이상 단순 비밀번호 수용.

### 🔄 변경 후
* **대문자 1개 이상 + 특수문자 1개 이상 + 8자 이상 필수 강제 정규식** 도입 (`^(?=.*[A-Z])(?=.*[!@#$%^&*()_+\-=\[\]{};':"\\|,.<>\/?]).{8,}$`).

### 💡 물리적 원리, Trade-off 및 극복 방안
1. **물리적 원리**:
   * 프론트엔드 자바스크립트 실시간 Regex 검사 + 백엔드 Spring DTO `@Pattern` 어노테이션 2중 수호.
2. **치러야 하는 대가 (Trade-off)**:
   * 유저의 가입 장벽 상승 및 타이핑 불일치 가능성.
3. **서비스/아키텍처 레벨 극복 방안**:
   * 프론트엔드에 `비밀번호` 및 `비밀번호 확인` 2중 필드 배치.
   * `✓ 8자 이상`, `✓ 대문자 1개 이상`, `✓ 특수문자 1개 이상` 배지와 `🟢 비밀번호가 안전하게 일치합니다` 메세지를 0ms 실시간 반응형 UI/UX로 시각화하여 사용성 저하를 완벽히 극복함.

## 3. 아키텍처 변경점 3: N:M 선호 스키장 / 라이딩 성향 대리키 중계 테이블 정규화

### 📌 변경 전
* `List<Long> resortIds` 를 회원 테이블 내 단일 문자열/JSON 컬럼으로 비정규화 저장 검토.

### 🔄 변경 후
* **`MemberResort` 및 `MemberRidingStyle` 대리키 `id` PK 기반 정규화 3NF 중계 테이블 구축**.

### 💡 물리적 원리, Trade-off 및 극복 방안
1. **물리적 원리**:
   * `member_id` + `resort_id` 복합 UNIQUE 인덱스를 구성하여 무결성을 보장하고, JPA 엔티티로 매핑하여 관계를 객체화함.
2. **치러야 하는 대가 (Trade-off)**:
   * 회원 프로필 조회 시 중계 테이블 조인에 따른 N+1 성능 저하 가능성.
3. **서비스/아키텍처 레벨 극복 방안**:
   * `JOIN FETCH` 쿼리를 적용하여 N+1 쿼리를 원천 차단하고 단 1번의 쿼리로 마스터 데이터와 연동 조회함.
