# 리조트별 한눈에 보기 페이지 (IKA-107, 2026-11-20)

## 배경

시즌 초 검색 수요는 "곤지암 개장일", "하이원 웹캠", "용평 날씨", "비발디 설질", "휘닉스 시즌권 가격"처럼 리조트 이름에 정보 이름이 붙는다. 눈팅에는 이 정보가 이미 다 있는데 메뉴별로 흩어져 있다.

| 정보 | 지금 있는 곳 | 리조트별 주소 |
| --- | --- | --- |
| 개장일, D-DAY | 홈 배너, 슬로프캠 머리의 배지, 시즌권 가격 표 | 없음 (브라우저에서 받아 그려 첫 HTML에 없음) |
| 기온 | 슬로프캠 머리의 칩 | 없음 (브라우저에서 받아 그림) |
| 슬로프캠 | `/resort-cam/{리조트}` | 있음, 사이트맵에 있음 |
| 슬로프 운영 현황 | `/slopes` 한 화면에 전체 | 없음 (`/slopes#리조트`, 브라우저에서 받아 그림) |
| 슬로프 제원, 코스 맵 | `/slopes/{리조트}` | 있음, 사이트맵에 있음 |
| 오늘의 설질 | 홈, `/resort-reports` | 없음 (리조트 필터는 화면 상태) |
| 카풀 | `/carpool` | 없음 (검색어) |
| 시즌권, 리프트권 가격 | `/tools/season-pass-prices` 표 | 없음 |

`/resort`는 예전 화면이 하드코딩 값을 보여 줘서 `/resort-cam`으로 넘기는 주소다.

### 이미 있는 것과 겹치는가

리조트별 주소는 두 종류가 이미 있고 사이트맵에도 들어 있다: `/resort-cam/{리조트}`(제목 "곤지암리조트 스키장 웹캠, 슬로프캠")와 `/slopes/{리조트}`(제목 "곤지암리조트 슬로프 제원과 코스 맵"). 둘 다 한 가지 정보의 상세 화면이다. 개장일, 기온, 운영 현황, 설질, 카풀, 가격은 리조트별 주소가 없고, 있는 화면에서도 브라우저가 나중에 받아 그려 첫 HTML에 들어가지 않는다. 그래서 "곤지암 개장일" 같은 검색에 답하는 문서가 없다.

결론: 같은 것이 이미 있지 않다. 새 페이지를 만들되 기존 두 주소와 검색어가 겹치지 않게 제목을 나눈다. 새 페이지 제목에는 웹캠, 제원을 넣지 않고 해당 블록에서 기존 상세 화면으로 보낸다.

## 고른 방향과 다른 후보

리조트마다 서버에서 그리는 공개 페이지 하나를 만들고, 리조트 목록 페이지를 둔다. 새 데이터 수집은 없다.

| 후보 | 고르지 않은 이유 |
| --- | --- |
| 리조트 구독 알림(개장, 설질 제보가 올라오면 알림) | 이미 온 회원을 다시 부르는 기능이다. 새 방문자를 데려오지 못한다. |
| 설질 제보 구조화(설질, 대기, 날씨를 고르는 칸) | 제보가 쌓여야 가치가 생긴다. 지금 하루 제보가 10건 안팎이라 검색 문서로 쓰기에 얇다. 쓰기 계약과 DB가 바뀐다. |
| 주간 눈 소식 자동 글 | 자동으로 만든 글을 게시판에 올리면 사람 글과 섞인다. 016 문서의 "내부 글을 재활용해 공개 검색 문서로 만들지 않는다", 013 실행안의 "대량 생성 금지"와 맞지 않는다. |
| 기존 `/resort-cam/{리조트}`에 블록을 더 붙이기 | 영상 여러 개를 재생하는 무거운 화면이고 제목이 웹캠이다. 개장일을 찾는 사람에게 맞지 않고, 블록이 영상 아래로 밀린다. |

고른 방향은 이미 있는 데이터만으로 되고, 검색 의도(리조트 이름 + 정보)와 문서가 1:1로 맞고, 각 블록이 기존 화면으로 이어져 흩어진 기능의 입구가 된다.

## 주소

- `/resorts`: 리조트 목록. 개장일, 운영 슬로프 수, 카메라 수.
- `/resorts/{리조트}`: 리조트 한눈에 보기. 13곳.

리조트 표기는 슬로프캠, 슬로프 제원과 같은 규칙(코드를 소문자로, 밑줄을 붙임표로)이다: `konjiam`, `welli-hilli`, `yongpyong`, `high1`, `jisan`, `muju`, `o2-resort`, `phoenix`, `vivaldi`, `eden-valley`, `elysian`, `alpensia`, `oak-valley`. 세 화면의 주소가 같은 표기라 사람이 주소를 고쳐 옮겨 다닐 수 있다. 한글 주소는 공유할 때 퍼센트 인코딩으로 길어져 쓰지 않았다.

리조트 목록의 기준은 슬로프캠 목록(`GET /api/v1/resort-cams`, 실패하면 프론트의 대체 목록)이다. 이름과 지역 표기도 이 목록 값을 그대로 쓴다. 목록에 없는 주소는 404다. 일본 리조트는 슬로프 제원에만 있고 개장일, 기온, 카풀 데이터가 없어 넣지 않는다.

기존 `/resort`(→ `/resort-cam` 이동)는 그대로 둔다. 예전 링크의 뜻이 슬로프캠이었기 때문이다.

규칙

- 개장일 표기는 기존 화면 규칙을 따른다. 리조트가 발표한 날짜는 "확정", 아니면 "예상". D-DAY는 개장 전일 때만 보이고 D+n은 쓰지 않는다. 확정일이 지나면 날짜만 보이고, 예상일이 지났는데 확정이 등록되지 않았으면 개장했다고 말하지 않고 "리조트 공지를 확인해 주세요"로 둔다.
- 기온은 관측 시각과 출처(리조트 공식, 기상청)를 같이 쓴다. "실시간"이라고 쓰지 않는다. 슬로프 현황도 갱신 시각을 쓴다.
- 가격은 조사 시점과 "대략값"임을 블록 안에 쓴다. 가격 표와 같은 상수를 읽어 두 화면 값이 어긋나지 않는다. 가격 데이터의 코드 표기(WELLIHILLI)는 밑줄을 빼고 맞춘다.
- 설질 제보는 회원이 쓴 짧은 글이다. 화면 블록에만 쓰고 제목, 설명, 구조화 데이터에는 넣지 않는다. 닉네임과 시각만 보이고 회원 종류를 구분하는 표시는 없다.
- 카풀은 목록 API가 이미 공개하는 값(제목, 집결지 표시명, 출발 시각)만 쓴다. 연락처, 좌표는 쓰지 않는다.
- 블록마다 기존 상세 화면으로 가는 링크를 둔다. 운영에 없는 기능으로 가는 링크는 없다. 제보는 홈에서만 쓸 수 있어 "홈에서 제보 남기기"로 적었다.
- 가입 안내는 화면 맨 아래 한 줄이다. 013 실행안의 "전체 화면 팝업이나 가입 유도 배너를 추가하지 않는다"에 맞춰 내용을 가리지 않는다.

## SEO

- 제목: `{리조트 이름} 개장일, 날씨, 슬로프 현황, 시즌권 가격 | 눈팅 SnowThing`. 13곳이 서로 다르고, 웹캠(`/resort-cam`)과 제원(`/slopes`) 제목과 겹치지 않는다.
- 설명: 지역, 리조트 이름, 개장일 요약(있을 때만. 예: "12월 11일 개장 예상"), 카메라 수를 실제 값으로 넣는다.
- canonical, Open Graph, 트위터 카드는 기존 `publicPageMetadata`를 쓴다. 이미지는 기본 이미지다.
- JSON-LD: `WebPage`에 `about: SkiResort`(이름, 나라, 지역)와 `BreadcrumbList`만 넣는다. 눈팅은 리조트 운영자가 아니라서 `SkiResort`를 페이지의 주체로 쓰거나 가격, 영업시간, 평점을 넣지 않는다.
- 첫 HTML에 리조트 이름, 개장일, 기온, 가격이 글자로 들어간다(서버 렌더링).
- 사이트맵에 `/resorts`와 리조트 13곳을 넣는다.
- 한계: 검색엔진의 수집, 색인, 순위는 보장할 수 없다.

## 캐시와 백엔드 부하

검색에서 들어오는 페이지라 방문자 수와 백엔드 호출 수가 비례하면 안 된다.

- 페이지는 요청마다 서버에서 그린다(`force-dynamic`). 오늘 날짜로 D-DAY를 계산하기 때문에 렌더 결과 자체를 오래 보관하면 자정 뒤에 틀린 값이 나간다.
- 데이터는 프론트 서버 프로세스 안에 잠깐 보관한다(`frontend/app/resorts/data.ts`). 슬로프캠 목록이 이미 쓰는 방식과 같다. Next 데이터 캐시(`revalidate`)를 쓰지 않은 이유: `force-dynamic` 페이지에서 fetch 캐시 동작이 Next 판마다 달라졌고, 기존 코드(`publicApi.ts`)도 쓰지 않기로 적어 두었다. 프로세스 안 보관은 동작이 코드에 그대로 보인다.
- 보관하는 것은 로그인 정보가 섞이지 않는 공개 조회뿐이다. 방문자 쿠키를 백엔드로 넘기지 않으므로 "삭제 가능 여부" 같은 개인 값은 항상 비로그인 기준이다.

| 조회 | 보관 시간 | 호출 단위 |
| --- | --- | --- |
| 슬로프캠 목록 | 5분 (기존) | 전체 1개 |
| 개장일 | 5분 | 전체 1개 |
| 슬로프 운영 현황 | 5분 | 전체 1개 |
| 슬로프 제원 요약 | 30분 | 전체 1개 |
| 오늘의 설질 | 1분 | 전체 1개 (리조트별로 나눠 씀) |
| 카풀 목록 | 2분 | 전체 1개 (리조트별로 나눠 씀) |
| 기온 | 2분 | 리조트마다 1개 |

- 리조트 페이지 한 번에 필요한 조회는 7개다. 모두 보관돼 있으면 백엔드를 0번 부르고, 아무것도 없으면 7번(동시에) 부른다. 목록 페이지는 3개.
- 방문자가 아무리 많아도 한 시간에 백엔드로 가는 호출의 상한은 개장일 12 + 현황 12 + 제원 2 + 설질 60 + 카풀 30 + 슬로프캠 12 + 기온 30 x 13곳 = 518번이다(프론트 컨테이너 하나 기준).
- 같은 조회가 동시에 여러 번 와도 진행 중인 요청 하나를 같이 기다린다.
- 조회 하나는 2초에서 끊는다. 실패하면 30분 안의 예전 값을 보여 주고, 없으면 그 블록만 "불러오지 못했습니다"로 둔다. 실패한 조회는 15초 동안 다시 부르지 않는다(백엔드가 느릴 때 모든 방문자가 2초씩 기다리지 않게).
- 카풀은 검색어 조회(`keyword`)를 쓰지 않는다. 검색어 조회에는 IP별 횟수 제한이 있는데 서버에서 부르면 모든 방문자가 프론트 서버 IP 하나로 묶인다. 전체 목록(최대 100건)을 받아 도착 리조트 이름으로 나눈다. 출발 전 모집글이 100건을 넘으면 최근 등록 100건 안에서만 찾는다.
- 백엔드 변경은 없다.

부작용

- 관리자가 개장일을 바꿔도 이 페이지에는 최대 5분 뒤에 보인다. 설질 제보는 최대 1분, 카풀은 최대 2분 늦다. 방금 쓴 사람은 홈, 설질, 카풀 화면에서 바로 확인할 수 있다.
- 프론트 컨테이너가 다시 뜨면 보관한 값이 비워진다.

## 화면

- 색은 `globals.css` 토큰만 쓰고 새 색을 만들지 않았다. 스타일은 `resorts.module.css`에 둔다.
- 모바일은 한 줄, 760px부터 두 줄 격자. 가격 블록은 전체 폭.
- 로딩: 서버에서 그려 내보내므로 첫 화면에 빈 블록이 없다. `loading.tsx`는 두지 않았다. 두면 본문이 스트리밍으로 나가서 없는 리조트 주소가 404가 아니라 200으로 답한다.
- 오류: 조회 실패는 블록마다 따로 처리한다. 그 밖의 예외는 기존 `app/error.tsx`가 받는다.

## 진입점

- 헤더와 모바일 메뉴에 "리조트 정보"(슬로프캠 앞).
- 홈 개장 D-DAY 배너의 "리조트별 보기"가 `/resort-cam` 대신 `/resorts`로 간다. 개장일을 보던 사람이 리조트별 개장일 목록으로 이어진다.
- 슬로프캠 머리, 슬로프 제원 머리에 "리조트 정보" 버튼.
- 시즌권 가격 표의 리조트 이름, 표 아래 관련 링크.
- 사이트맵.

분석 SDK는 없다. 운영 반영 뒤 아래로 본다.

- Google Search Console, 네이버 서치어드바이저에서 `/resorts/` 주소의 색인 수, 노출, 클릭, 검색어(리조트 이름 + 개장일, 날씨, 시즌권).
- 프론트 접근 로그에서 `/resorts/` 요청 수와, 그 뒤 `/resort-cam/`, `/carpool`, `/signup`으로 이어진 요청(Referer).
- 반영 전후 2주의 가입 수(관리자 대시보드).

## 사용자 결정 필요

- 메뉴 이름 "리조트 정보"와 헤더에서의 위치.
- 홈 개장 배너가 슬로프캠 대신 리조트 목록으로 가도 되는지.
- 페이지 제목에 넣을 검색어 순서(지금: 개장일, 날씨, 슬로프 현황, 시즌권 가격).
- 설질 제보를 이 페이지에 그대로 보여도 되는지(장난 글이 섞일 수 있다. 지금은 오늘의 설질 화면과 같은 공개 범위).
