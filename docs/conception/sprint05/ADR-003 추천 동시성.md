# ADR-003 추천 동시성 제어

- 상태: Accepted
- 결정일: 2026-09-19
- 대상: 게시글 `LIKE`·`DISLIKE`, `post_reaction`, `post.like_count`, `post.dislike_count`
- 실험 환경: MySQL 8.0.46 InnoDB, 로컬 `snowthing_test`, 동시 요청 100건

## 문제

추천 row는 사용자의 추천 사실을 나타내는 원본이고, `like_count`와 `dislike_count`는 목록 조회를 위해 저장한 역정규화 값이다. 기존 토글 API는 조회한 값에 따라 추천을 만들거나 지웠기 때문에 같은 요청을 재전송하면 의도와 반대 상태가 될 수 있었다. 카운터를 엔티티에서 읽어 증가시킨 뒤 저장하는 Read-Modify-Write 방식은 여러 트랜잭션이 같은 값을 읽으면 Lost Update가 발생한다.

이번 결정은 추천 100건을 성공시키는 데 목적을 두지 않는다. 실패를 재현하고, 지켜야 할 불변식을 정한 뒤 세 후보를 같은 조건에서 비교해 운영 방식과 복구 절차를 선택하는 것이 목적이다.

## 불변식

- `like_count`는 `LIKE` row 수와 같아야 한다.
- `dislike_count`는 `DISLIKE` row 수와 같아야 한다.
- 두 카운터는 음수가 될 수 없다.
- 회원은 게시글과 반응 종류별로 활성 row를 최대 1개만 가질 수 있다.
- 익명 사용자는 게시글·익명 식별자·반응 종류별로 활성 row를 최대 1개만 가질 수 있다.
- 반복 PUT의 최종 상태는 반응 row 1개다.
- 반복 DELETE의 최종 상태는 반응 row 0개다.
- row 변경과 카운터 변경 중 하나라도 실패하면 둘 다 롤백돼야 한다.

## 실패 재현

Read-Modify-Write 실험에서는 100개 트랜잭션이 카운터를 먼저 읽고 대기하도록 했다. 모든 트랜잭션이 `reaction_count=0`을 읽은 것을 확인한 뒤, 각자 읽은 값에 1을 더한 절대값을 저장하게 했다.

| 반복 | 요청 | 추천 row | 최종 카운터 | 예외 | 실행 시간 |
|---:|---:|---:|---:|---:|---:|
| 1 | 100 | 100 | 1 | 0 | 5,004ms |
| 2 | 100 | 100 | 1 | 0 | 464ms |
| 3 | 100 | 100 | 1 | 0 | 465ms |

첫 실행은 커넥션 풀 확장과 초기화 비용을 포함한다. 세 번 모두 100개 트랜잭션이 `0`을 읽었고 마지막 UPDATE가 앞선 결과를 덮어써 카운터가 1로 남았다.

## 후보 비교

모든 후보는 같은 테이블과 데이터에서 100개 스레드를 준비한 뒤 동시에 실행했다. 각 후보를 세 번 반복했고 정합성, 예외, 재시도, 실행 시간을 확인했다.

| 후보 | 카운터/row | 예외 | 재시도 | 실행 시간 |
|---|---|---:|---:|---:|
| 원자적 UPDATE | 100/100, 3회 모두 일치 | 0 | 0 | 440ms, 467ms, 436ms |
| 낙관적 락 | 100/100, 3회 모두 일치 | 0 | 4,950회, 4,948회, 4,950회 | 2,998ms, 2,842ms, 2,869ms |
| 비관적 락 | 100/100, 3회 모두 일치 | 0 | 0 | 455ms, 477ms, 465ms |

### 원자적 UPDATE

`count = count + 1`을 DB가 한 문장으로 처리한다. 애플리케이션이 이전 값을 가져와 계산하지 않으므로 Lost Update가 발생하지 않았다. 단순 카운터에 맞고 별도 version 재시도가 필요 없다.

### 낙관적 락

`version`이 같은 경우에만 UPDATE하고 충돌하면 트랜잭션을 처음부터 다시 실행했다. 정합성은 지켰지만 모든 요청이 같은 게시글을 수정하는 조건에서 재시도가 약 4,950회 발생했다. 충돌이 드문 데이터에는 맞지만 인기 게시글 카운터에는 비용이 컸다.

### 비관적 락

`SELECT ... FOR UPDATE`로 게시글 row를 잠근 뒤 추천 row와 카운터를 변경했다. 정합성과 실행 시간은 원자적 UPDATE와 비슷했지만, 요청이 게시글 락을 기다리며 직렬화된다. 도메인 상태를 여러 단계로 판단해야 할 때는 이해하기 쉽지만 단순 증감까지 항상 명시적으로 잠글 필요는 없었다.

## 실험 중 추가로 발견한 문제

처음에는 추천 row를 INSERT한 뒤 게시글 카운터를 UPDATE했다. 실제 외래키가 있는 구조에서 INSERT는 부모 게시글 row에 공유 락을 잡고, 뒤이은 UPDATE는 배타 락으로 승격하려 했다. 100개 트랜잭션이 같은 순서로 실행되자 lock upgrade deadlock이 발생했다.

이를 숨기기 위해 무조건 재시도하지 않고 락 획득 순서를 통일했다.

```text
PUT
게시글 카운터 원자 증가로 부모 row 배타 락 획득
→ INSERT IGNORE 추천 row
→ 이미 존재하면 같은 트랜잭션에서 증가분 보상

DELETE
게시글 row FOR UPDATE
→ 추천 row DELETE
→ 실제 삭제된 경우에만 카운터 원자 감소
```

모든 경로가 게시글 row를 먼저 확보한 뒤 `post_reaction`을 변경하므로 부모·자식 락 순서가 같다.

## 결정

원자적 UPDATE를 기본 방식으로 채택한다. 추천 생성은 카운터를 먼저 원자 증가시키고 `INSERT IGNORE` 결과가 중복이면 증가분을 되돌린다. 추천 취소는 게시글 row를 잠근 뒤 DELETE 결과가 1일 때만 카운터를 감소시킨다. 생성·삭제와 카운터 변경은 하나의 트랜잭션에서 처리한다.

API는 의도를 분명하게 나눈다.

```http
PUT    /api/v1/posts/{publicId}/reaction?type=LIKE
DELETE /api/v1/posts/{publicId}/reaction?type=LIKE
```

`DISLIKE`도 같은 API와 동시성 제어를 사용한다. 기존 `POST /reactions` 토글은 기존 클라이언트 호환용으로만 남기고 제거 대상으로 표시한다.

DB UNIQUE는 다음 두 제약을 유지한다.

- `(post_id, member_id, type)`
- `(post_id, anonymous_voter_id, type)`

UNIQUE는 중복 row를 막는 최종 안전장치다. 카운터 Lost Update나 row와 카운터의 트랜잭션 순서를 해결하는 락의 대안은 아니다.

## 선택안의 단점

- 같은 게시글의 쓰기는 결국 게시글 row lock에서 직렬화된다.
- 중복 PUT도 카운터를 증가한 뒤 보상하므로 UPDATE 두 번이 발생한다.
- `INSERT IGNORE`는 MySQL에 종속되고 경고 처리 범위를 확인해야 한다.
- 인기 게시글 하나에 쓰기가 과도하게 몰리면 lock wait가 길어질 수 있다.
- 기존 토글 API가 남아 있는 동안 두 계약을 함께 관리해야 한다.

현재 규모에서는 구현과 운영이 단순하고, 원본 row와 역정규화 카운터를 한 트랜잭션에서 맞출 수 있다는 이점이 더 크다고 판단했다.

## 재시도와 타임아웃

애플리케이션 내부에서 모든 예외를 자동 재시도하지 않는다. UNIQUE 중복은 멱등 성공으로 처리하지만, deadlock이나 lock wait timeout은 트랜잭션을 롤백하고 명시적인 오류로 남긴다. 무제한 재시도는 장애 시 요청 적체를 키울 수 있다. 운영 지표에서 일시적인 deadlock이 확인되면 짧은 횟수의 제한된 재시도와 jitter를 별도 결정한다.

클라이언트는 네트워크 오류 시 같은 PUT 또는 DELETE를 다시 보낼 수 있다. 명령 자체가 멱등하므로 최종 상태는 바뀌지 않는다.

## 검증 결과

- 실제 `post`·`post_reaction` 통합 테스트의 주요 동시성 시나리오를 각각 세 번 반복했다.
- 서로 다른 회원 100명의 동시 PUT: 매회 성공 100, 오류 0, row 100, `like_count` 100, 576~673ms
- 동일 회원의 동시 PUT 100건: 매회 성공 100, 오류 0, 실제 변경 1, row 1, `like_count` 1, 257~277ms
- 동일 회원의 동시 DELETE 100건: 매회 성공 100, 오류 0, 실제 변경 1, row 0, `like_count` 0, 208~231ms
- 동일 회원의 PUT 50건과 DELETE 50건: 매회 성공 100, 오류 0, 최종 row와 카운터 일치, 511~531ms
- 동일 익명 식별자의 동시 PUT 100건: 매회 성공 100, 오류 0, 실제 변경 1, row 1, `like_count` 1, 476~505ms
- 동일 익명 식별자의 동시 DELETE 100건: 매회 성공 100, 오류 0, 실제 변경 1, row 0, `like_count` 0, 564~591ms
- 동일 익명 식별자의 PUT 50건과 DELETE 50건: 매회 성공 100, 오류 0, 최종 row와 카운터 일치, 583~618ms
- 추천 row INSERT 강제 실패: 먼저 증가한 카운터까지 롤백
- 카운터 감소 강제 실패: 삭제한 추천 row까지 롤백
- 회원·익명 중복 row 직접 INSERT: 각각 DB UNIQUE가 차단
- `like_count=-1` 직접 UPDATE: MySQL 오류 코드 3819로 CHECK 제약 위반 확인
- 응답 유실을 가정한 같은 PUT·DELETE 재전송: `active` 상태와 카운터 유지

통합 테스트는 요청 수, 성공 수, 오류 수, 실제 상태 변경 수, 전체 실행 시간을 로그로 남긴다. 이번 실행에서는 모든 동시성 시나리오의 오류가 0건이었으므로 예외 유형과 재시도 횟수도 0이다. 애플리케이션은 deadlock과 lock wait timeout을 자동 재시도하지 않으므로 이런 오류가 생기면 테스트가 실패하고 원본 예외가 결과에 남는다.

## 장애 탐지와 복구

Reconciliation은 반응 row를 원본으로 보고 게시글별 `COUNT(*)`와 저장된 카운터를 비교한다. 불일치를 찾으면 게시글 ID, 반응 종류, 수정 전 값과 실제 row 수를 기록한다. 자동 수정 스케줄러는 이번 범위에 넣지 않았다. 관리자가 원인을 확인한 뒤 `ReactionService.reconcile()`을 실행하면 같은 트랜잭션에서 카운터를 실제 row 수로 맞추고 전후 값을 로그로 남긴다.

Reconciliation은 정상 쓰기 경로의 오류를 감추는 수단이 아니다. 불일치가 발견되면 먼저 같은 시각의 deadlock, timeout, 수동 SQL, 배포 이력을 확인한다.

운영 절차는 다음 순서로 고정한다.

1. 읽기 작업으로 `findCountMismatches(LIKE)`와 `findCountMismatches(DISLIKE)` 결과를 수집한다.
2. 결과가 있으면 게시글 public ID, 반응 종류, 저장 카운터, 실제 row 수, 확인 시각을 장애 기록에 남긴다.
3. 같은 시각의 애플리케이션 오류, MySQL deadlock·lock wait, 수동 SQL과 배포 이력을 확인한다.
4. 원인이 확인되고 원본 `post_reaction`을 신뢰할 수 있을 때만 관리자가 복구를 승인한다.
5. 승인된 게시글에 `reconcile(publicId, type)`을 실행하고 서비스 로그의 `before`, `after`, `changed`를 증거로 보존한다.
6. 불일치 조회를 다시 실행해 결과가 0건인지 확인한다.

현재는 자동 스케줄러나 외부 관리자 API를 열지 않는다. 운영 데이터 변경 권한이 생기는 기능이므로 실행 주체와 인증 방식을 정하지 않은 상태에서 노출하지 않는 편이 안전하다. 정기 점검이 필요해지면 읽기 전용 탐지를 먼저 스케줄링하고, 수정은 승인 절차를 유지한다.

## 재검토 조건

- 인기 게시글의 lock wait 또는 deadlock이 운영 임계치를 지속해서 넘는 경우
- 단일 MySQL writer가 처리량 한계에 도달한 경우
- 추천 이벤트를 다른 서비스가 소비해야 하는 경우
- 카운터의 즉시 일관성보다 쓰기 가용성이 더 중요해지는 경우

이때는 outbox와 메시지 큐, 비동기 집계, Redis counter 같은 최종 일관성 구조를 비교한다. 전환하더라도 원본 추천 row, 이벤트 중복 제거, 재처리와 reconciliation이 함께 설계돼야 한다.
