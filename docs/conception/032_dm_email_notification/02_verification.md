# 쪽지 도착 메일 검증 기록

- 측정일: 2026-11-17
- 환경: 로컬 Windows, Docker MySQL 8.0, 가짜 SES HTTP 서버. 운영 DB와 실제 SES는 쓰지 않았다.
- 세는 기준: 같은 발송 요청에 대한 공급자(가짜 SES) 수락 횟수. HTTP 요청 수, 수락 수, 최종 DB 상태를 따로 적는다.

## 1. 자동 테스트

`./gradlew spotlessCheck test` 전체 통과 (테스트 1304건, 실패 0, 건너뜀 1건은 기존 테스트). 이번에 추가한 쪽지 메일 테스트는 31건이다. 관리자 요약 테스트는 전체 실행 뒤에 더했고, 쪽지 메일 테스트 31건을 따로 다시 돌려 통과했다.

- `DmMailOutboxIntegrationTest` 27건: 실제 MySQL과 가짜 SES. 처리기에 시각을 넘겨 쿨다운과 lease 만료를 재현한다.
- `DmMailComposerTest` 4건: 메일 문구.

가입 경로는 단위 테스트로 확인했다. `VerifiedMemberRegistrationServiceTest`, `SocialAuthServiceTest`에서 신규 가입 때 `initializeForNewMember`가 불린다.

## 3. 수동 실험 (프로세스 단위)

같은 jar로 앱 프로세스를 띄우고 같은 MySQL과 가짜 SES(별도 프로세스)를 보게 했다. 폴링 간격은 0.2초다. 쪽지와 발송 요청은 SQL로 한 트랜잭션에 넣어, 쪽지 트랜잭션이 커밋된 직후와 같은 상태를 만들었다.

### 실험 1. 워커 두 개 경합

- 조건: 앱 프로세스 두 개(포트 18081, 18082) 동시 실행. 받는 사람 40명, 받는 사람마다 쪽지 3개(발송 요청 120행)를 한 번에 커밋. 가짜 SES 수락 지연 0.3초.

| 항목 | 결과 |
|---|---|
| 가짜 SES HTTP 요청 | 40 |
| 가짜 SES 수락 | 40 |
| 두 통 이상 받은 받는 사람 | 0 |
| DB 최종 상태 | ACCEPTED 120 |
| MessageId 수와 묶인 행 수 | 40개, 각 3행 (묶음이 쪼개지지 않음) |
| 처리 분담 (로그) | 프로세스 1: 20명, 프로세스 2: 20명 |

### 실험 2. 커밋 후 워커가 돌기 전 종료, 재기동

- 조건: 앱 프로세스를 모두 내린 상태에서 받는 사람 5명, 발송 요청 15행을 커밋. 확인 시 PENDING 15. 그 뒤 프로세스 하나를 다시 띄움.

| 항목 | 결과 |
|---|---|
| 내려가 있는 동안 | PENDING 15 (요청이 사라지지 않음) |
| 재기동 후 HTTP 요청, 수락 | 5, 5 |
| DB 최종 상태 | ACCEPTED 15 |

서버가 꺼져 있는 동안 발송은 멈추고, DB가 남아 있으면 재기동 후 이어서 처리한다. 서버 장애 중에도 서비스가 계속된다는 검증은 아니다.

### 실험 3. SES 수락 직후, 결과 기록 전 강제 종료

- 조건: lease 15초. 가짜 SES는 요청을 수락한 뒤 2.5초 동안 응답하지 않는다(앱 시도 제한 3초). 수락이 기록되는 즉시 앱 프로세스를 강제 종료했다. 이후 가짜 SES를 정상 수락 모드로 바꾸고 앱을 다시 띄웠다. 재발송이 일어나면 요청 수가 늘어 보이게 하려는 것이다.

| 시점 | HTTP 요청 | 공급자 수락 | DB 상태 |
|---|---|---|---|
| 종료 직후 | 1 | 1 | PROCESSING, attempts 1, lease_until 23:27:16 |
| 재기동 후 lease 만료 (23:27:19) | 1 | 1 | UNKNOWN, LEASE_EXPIRED |
| 그 뒤 5초 더 관찰 | 1 | 1 | UNKNOWN |

메일은 실제로 한 통 나갔지만 DB만으로는 그 사실을 알 수 없다. 기본 정책대로 자동 재발송은 0회이고, 운영자가 확인할 UNKNOWN으로 격리됐다.

## 4. 측정 중 관찰: 제한 시간이 공급자 응답보다 짧을 때

성능 측정 첫 실행에서 테스트용 짧은 제한 시간(시도 0.6초, 전체 0.9초)을 그대로 두고 가짜 SES 지연을 1초로 줬다. 그 결과 Outbox 쪽 60건이 모두 UNKNOWN이 됐는데, 가짜 SES는 그중 59건을 실제로 수락했다. 수락 후 응답 유실(타임아웃 B)이 대량으로 재현된 셈이다. SES 호출 제한 시간은 공급자의 정상 응답 시간보다 충분히 길어야 하고, UNKNOWN이 늘면 먼저 제한 시간과 공급자 지연을 확인해야 한다. 이 실행은 성능 수치에서 제외했다.

## 5. 프론트

- `npm run lint`, `npm run build` 통과.
- 화면: 헤드리스 Chrome으로 계정 세 개(신규 회원, 기존 회원, 소셜 내부 주소)를 로그인해 데스크톱 1280px과 모바일 390px에서 찍었다.
  - 신규 회원: 스위치 켜짐. 누르면 꺼지고 새로고침 뒤에도 꺼짐 유지, 다시 누르면 켜짐.
  - 기존 회원: 스위치 꺼짐. 누르면 켜지고 새로고침 뒤에도 유지.
  - 소셜 내부 주소: 스위치 꺼짐, 비활성, "메일을 받을 수 있는 인증된 이메일이 없어 메일 알림을 켤 수 없어요" 안내.
  - 로그인하지 않으면 스위치가 보이지 않고 쪽지함이 로그인 화면으로 보낸다.
  - 다크 모드는 확인하지 않았다.

## 6. 하지 않은 것
