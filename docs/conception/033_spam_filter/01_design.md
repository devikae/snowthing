# 금칙어 조용한 보류와 IP 대역 차단 (IKA-96, 2026-11-19)

## 왜

- 익명게시판에 카지노 광고가 반복해서 올라왔다(11/16 글 213, 11/19 글 231). 두 글 모두 IPv6 `2001:fd8:c11e:2e00::/64`에서 왔고 호스트 부분만 달랐다.
- IP 차단은 라이브톡에만 있었고 주소 하나만 막았다. IPv6은 같은 집에서도 뒤쪽 주소가 계속 바뀌어 주소 하나 차단으로는 못 막는다.
- 글 내용으로 거르는 장치가 없었다.

## 범위

- 포함: 금칙어 목록(관리자 관리, 메모리 캐시), 글과 댓글 작성, 수정 때 조용한 보류, 관리자 검토 화면(공개 전환, 삭제, IP 대역 차단), CIDR 대역 차단을 글 작성, 댓글 작성, 라이브톡에 공통 적용.
- 제외: 중고장터와 카풀 글(로그인 전용이고 상태 의미가 달라 각자 작성 흐름이 있다), 라이브톡 금칙어, 한글 자모 분리 우회(ㅋㅏ지노), 서버 여러 대 사이 캐시 동기화(지금은 한 대).

## A. 금칙어 조용한 보류

### 동작

- 금칙어가 든 글이나 댓글도 저장은 성공하고 응답도 평소와 같다. 다른 사람에게만 보이지 않는다. 광고를 올린 사람이 걸린 것을 알아채고 표현을 바꾸지 못하게 하려는 선택이다.
- 관리자 글은 검사하지 않는다. AI 회원은 다른 회원과 똑같이 검사한다(서비스의 같은 작성 흐름을 탄다). AI 회원만 다르게 보이는 신호는 없다.
- 작성자 본인은 평소처럼 본다.
  - 회원: 회원 ID가 같은 로그인 세션. 봇 위임 토큰과 API 토큰은 제외한다(봇이 보류 글을 공개 채팅에 옮기지 못하게).
  - 비회원: 같은 IP이고 보류한 뒤 1시간 안. 계정이 없어 IP 말고 본인을 알 방법이 없다. 같은 IP를 쓰는 다른 사람(공유기, 통신사 공용 IP)에게 오래 보이지 않게 시간을 짧게 둔다.
- 보이는 곳: 상세, 댓글 목록, 게시판 첫 쪽(본인 글을 끼워 넣는다). 보이지 않는 곳: 다른 사람의 목록과 상세(404), 키워드 검색, AI 근거 검색, AI 회원 읽기, 알림과 푸시, 댓글 수.

### 상태를 어디에 두나

| 대상 | 방법 | 이유 |
|---|---|---|
| 글 | `post.status = 'FILTER_HOLD'` (새 값) | 공개 목록, 검색, 근거 검색, AI 회원 읽기, 반응, 신고가 모두 `status = NORMAL`만 받는다. 새 값 하나로 모든 공개 경로에서 빠진다. 신고 임시조치(`TEMPORARY_HOLD`)는 작성자에게 "임시조치됐다"고 알리는 흐름이라 섞지 않았다. 응답의 status는 `publicView()`로 NORMAL처럼 내보낸다. |
| 댓글 | `comment.filter_state = 'HELD'` + `is_deleted = true` | 댓글은 상태 컬럼이 없고 공개 경로가 `is_deleted = false`로 거른다. 신고 임시조치(`moderation_held`)와 같은 방식으로 삭제 상태를 함께 켜서 놓친 조회가 있어도 숨는 쪽으로 실패하게 했다. 댓글 목록 쿼리만 작성자 본인에게 이 행을 평소 댓글처럼 돌려준다. 다른 사람에게는 "삭제된 댓글" 자리도 남기지 않는다. |

- `content_filter_hold` 표는 검토 목록과 비회원 작성자 확인에 쓰는 기록이다. 공개 여부의 기준은 원문 상태다. 처리하면 줄을 지우고 이력은 관리자 조치 기록에 남긴다.
- 고르지 않은 안: 글에 보류 플래그 컬럼을 따로 두는 방법. 공개 조회 30여 곳에 조건을 더해야 하고 하나라도 빠지면 광고가 보인다.

### 수정과 삭제

- 작성자가 금칙어를 넣어 고치면 그때 보류한다. 보류 글을 깨끗하게 고치면 다시 공개한다(고친 내용도 매번 검사하므로 안전하다).
- 작성자는 보류된 글과 댓글을 평소처럼 고치고 지운다. 보류 댓글을 지우면 `REJECTED`가 되어 아무에게도 보이지 않는다.
- 댓글 수는 보류 댓글을 세지 않는다. 공개 전환하면 하나 올린다. 공개 전환 때 알림은 다시 보내지 않는다(늦게 가는 알림이 더 혼란스럽다).

### 금칙어 비교

- 글과 금칙어를 같은 방식으로 정리한 뒤 포함 여부를 본다: HTML 태그와 엔티티 제거, NFKC(전각 문자를 보통 글자로), 소문자, 글자와 숫자만 남김.
- "카 지 노", "카.지.노", "카&lt;b&gt;지&lt;/b&gt;노", 보이지 않는 문자를 끼운 표기를 모두 잡는다.
- 띄어쓰기를 무시하므로 짧은 금칙어는 다른 단어 사이에 걸칠 수 있다. 그래서 초기 목록은 광고에만 쓰는 말로 했다.
  - 넣음: 카지노사이트, 온라인카지노, 바카라, 토토사이트, 슬롯사이트, 홀덤사이트, 먹튀검증, 가입머니
  - 뺌: 카지노(하이원 카지노), 토토(토토로), 먹튀(카풀비 먹튀). 필요하면 관리자 화면에서 더한다.
- 등록은 정리한 값이 2자 이상 50자 이하. 정리한 값이 같으면 중복으로 막는다.
- 목록은 메모리에 두고 관리자가 바꾸면 커밋 뒤 다시 읽는다. 배포나 재시작이 필요 없다.

### 비회원 작성자의 상세 화면

- 상세 첫 화면은 Next 서버가 비로그인 기준으로 받는다. 이 요청의 IP는 Next 서버라서 보류 글은 404가 되고, 세션 쿠키가 없으면 404 페이지로 끝난다.
- 글을 쓰거나 고친 브라우저에 `snowthing_recent_write=<글 ID>` 쿠키(1시간)를 남긴다. 이 쿠키가 그 글 ID와 같으면 404 페이지 대신 브라우저가 상세를 다시 부르고, 백엔드는 실제 IP로 작성자를 확인한다.
- 모든 작성에 똑같이 남기므로 쿠키로 보류 여부를 알 수 없다. 권한 판단에는 쓰지 않는다(판단은 백엔드의 IP와 시간).
- 게시판 목록도 이 쿠키가 있으면 서버 첫 화면 대신 브라우저가 다시 받아 본인 글이 첫 쪽에 보인다.

## B. IP 대역 차단

- 저장은 기존 `chat_banned_ip` 표를 그대로 쓴다. `banned_ip`에 단일 IP나 CIDR 대역을 넣는다. 기존 단일 IP 차단은 /32, /128 대역으로 읽혀 그대로 동작한다. 표 이름 변경은 배포 중 옛 애플리케이션이 깨져서 하지 않았다.
- 서비스 이름도 `ChatIpBanService` 그대로 둔다(진행 중인 PR #152와 겹치지 않게). 하는 일은 공통 차단 목록이다.
- 적용: 게시글 작성, 댓글 작성, 라이브톡 전송. 관리자는 글, 댓글 작성에서 제외한다.
- 거절: 글과 댓글은 `403 COMMON_007 "지금은 글을 쓸 수 없습니다. 잠시 후 다시 시도해 주세요."`. 차단 여부와 대역을 알려 주지 않는다. 라이브톡은 기존 응답 그대로다.
- 확인: 활성 차단을 메모리 목록으로 들고 대역마다 비교한다. 수십 건이라 선형 비교로 충분하다. 차단, 해제 뒤 커밋되면 DB에서 다시 읽는다.
- 겹치는 차단: 줄마다 따로 비교하므로 같은 IP나 겹치는 대역에 여러 줄이 있으면 가장 늦게 끝나는 차단까지 막힌다. 한 줄을 풀어도 남은 줄은 그대로 동작한다(PR #152의 규칙과 같다).
- 입력 검사: 숫자 IP만 받는다(호스트 이름을 DNS로 찾지 않는다). 너무 넓은 대역은 막는다(IPv4 /16 미만, IPv6 /32 미만). 저장할 때 호스트 비트를 지워 같은 대역을 같은 값으로 적는다.
- 보류 항목의 "이 IP 대역 차단": IPv6은 /64, IPv4는 주소 하나를 30일 막는다. IPv4는 통신사 공용 IP가 많아 대역으로 넓히지 않는다.
- 클라이언트 IP는 기존 `ClientIpResolver`(사설망 프록시 뒤의 X-Real-IP, X-Forwarded-For)를 그대로 쓴다.
- 관리자 화면은 기존 `/admin/chat` 화면을 "IP 차단"으로 바꿔 쓴다. 새 화면을 만들지 않았다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | /api/v1/admin/banned-words | 금칙어 목록 (최근 등록 순, ID 보조 정렬) |
| POST | /api/v1/admin/banned-words | `{ "word": "..." }` 추가. 형식 400 ADMIN_009, 중복 409 ADMIN_010 |
| DELETE | /api/v1/admin/banned-words/{id} | 삭제 |
| GET | /api/v1/admin/filter-holds?page=&size= | 보류 목록 (최근 보류 순, ID 보조 정렬) |
| POST | /api/v1/admin/filter-holds/{id}/release | 공개 전환 |
| DELETE | /api/v1/admin/filter-holds/{id} | 삭제 (글은 일반 삭제 흐름) |
| POST | /api/v1/admin/filter-holds/{id}/ban-ip | 작성자 IP 대역 30일 차단 |
| GET, POST, DELETE | /api/v1/admin/chat/banned-ips | 기존 API. 이제 CIDR 대역도 받는다. 형식 400 ADMIN_007, 너무 넓음 400 ADMIN_008 |

- 모두 `/api/v1/admin/**`라 ROLE_ADMIN만 부른다. 조치는 관리자 조치 기록에 남는다(BANNED_WORD_CREATE, BANNED_WORD_DELETE, FILTER_HOLD_RELEASE, FILTER_HOLD_DELETE, CHAT_IP_BAN, CHAT_IP_UNBAN).
- 기존 공개 API의 요청과 응답 형식은 바뀌지 않는다. 상세, 목록, 댓글 조회는 서버가 요청 IP를 함께 본다.

## 테이블 (053 마이그레이션)

- `banned_word(banned_word_id, word, normalized_word UNIQUE, created_at)`
- `content_filter_hold(content_filter_hold_id, target_type, target_id, post_id, member_id, writer_ip, matched_word, held_at)`, UNIQUE(target_type, target_id), 인덱스: 목록(held_at, id), 회원(member_id), 비회원 확인(writer_ip, held_at)
- `comment.filter_state VARCHAR(10) NULL` 추가 (INSTANT)
- `chat_banned_ip` 표 설명만 바꾼다. `post.status`는 VARCHAR(20)이라 변경 없음.
- 추가만 하므로 마이그레이션을 먼저 적용하고 배포한다. 여러 번 실행해도 안전하다.

## 알려진 한계

- 비회원 작성자는 1시간이 지나거나 다른 IP(와이파이에서 LTE)로 바꾸면 자기 보류 글을 못 본다.
- 회원 작성자도 `snowthing_recent_write` 쿠키가 사라진 뒤(1시간)에는 게시판 목록에서 자기 보류 글을 못 본다. 상세 링크로는 계속 본다.
- 보류 글에 작성자가 반응(추천)이나 스크랩을 누르면 기존 공개 글 검사로 실패한다.
- 금칙어 캐시와 차단 캐시는 서버마다 따로다. 서버를 여러 대로 늘리면 다른 서버는 재시작 전까지 옛 목록을 쓴다.
