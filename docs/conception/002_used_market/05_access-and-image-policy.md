# 중고장터 접근·개인정보·이미지 정책

- 문서 번호: `POLICY-USED-MARKET-001`
- 상태: Draft
- 작성일: 2026-09-28
- 기반 문서: [`01_requirements.md`](./01_requirements.md), [`04_api-spec.md`](./04_api-spec.md)

## 1. 보호 대상

중고장터의 실제 거래 정보는 로그인 회원 전용이다. 보호 범위는 다음과 같다.

- 상품 분류 API
- 판매글 목록·검색·상세
- 판매글 작성·수정·상태 변경·삭제
- 판매글 댓글과 대댓글
- 상세 화면의 판매자 연락처

홈 공개 미리보기는 예외다. 최신 판매글의 `publicId`와 썸네일 URL만 최대 4건 공개하며 제목·가격·상태·판매자·연락처는 공개하지 않는다. 이번 범위에서는 CloudFront 이미지 객체까지 회원 전용으로 만들지 않고 기존 게시판과 같은 공개 CDN 이미지 URL을 사용한다.

## 2. 인증과 인가

### 2.1. 인증

세션 쿠키 `JSESSIONID`를 사용한다. 공개 미리보기를 제외한 비로그인 요청은 `401 Unauthorized`로 거부한다.

프런트엔드에서 로그인 화면으로 이동시키거나 메뉴를 숨기는 처리는 사용자 경험을 위한 보조 수단이다. 실제 보호는 Spring Security와 서비스 계층에서 적용한다.

### 2.2. 인가

| 주체 | 허용 범위 |
|---|---|
| 로그인 회원 | 목록·검색·상세·등록·댓글 |
| 작성자 | 본인 판매글 수정·거래 상태 변경·삭제 |
| 관리자 | 전체 조회·숨김·차단·복원·삭제 |
| 비로그인 | 홈 썸네일 공개 미리보기만 허용 |

관리자는 판매자의 가격, 연락처, 제목, 본문을 대신 수정하지 않는다. 운영 상태만 관리한다.

### 2.3. 계층별 적용

1. `SecurityConfig`는 `GET /api/v1/market-listings/preview`만 정확한 경로로 먼저 공개하고, `/api/v1/market/**`, 나머지 `/api/v1/market-listings/**`에는 인증을 요구한다.
2. Controller는 `CustomUserDetails`가 없는 요청을 서비스에 넘기지 않는다.
3. Service는 작성자와 관리자 권한을 다시 검사한다.
4. Repository는 권한 결정을 담당하지 않는다.

서비스 검증이 필요한 이유는 기존 댓글과 추천 경로가 `/posts/{publicId}`를 사용하기 때문이다. URL 규칙만 보호하면 기존 경로를 통해 정책을 우회할 수 있다.

공개 예외는 HTTP 메서드와 정확한 경로를 함께 지정한다. 넓은 GET 패턴을 허용하면 목록과 상세까지 공개될 수 있으므로 `/api/v1/market-listings/**` 전체를 `permitAll`로 두지 않는다.

## 3. 일반 게시판 우회 차단

중고장터는 내부적으로 `Post`를 사용하므로 다음 경로를 명시적으로 차단한다.

- 일반 게시글 전체 목록에서 `MARKET` 제외
- 일반 게시글 카테고리 목록에서 `MARKET` 제외
- 일반 게시판 카테고리 마스터 응답에서 내부용 `MARKET` 제외
- 실시간 베스트에서 `MARKET` 제외
- `POST /api/v1/posts`에서 `categoryCode = MARKET` 거부
- `PUT /api/v1/posts/{publicId}`에서 중고장터 글 수정 거부
- `GET /api/v1/posts/{publicId}`에서 중고장터 글 상세 응답 거부
- 추천·비추천 API에서 중고장터 글 거부

일반 상세 경로로 접근한 중고장터 글은 존재 여부를 드러내지 않도록 `404 Not Found`로 처리한다. 정상적인 중고장터 경로에 비로그인으로 접근하면 로그인 필요 상태를 알 수 있도록 `401 Unauthorized`를 반환한다.

## 4. 댓글 접근 정책

기존 댓글 API는 공개 게시글을 지원하므로 Security URL 규칙만 전체 인증으로 바꿀 수 없다. 댓글 서비스가 대상 Post의 종류를 확인해 다음 정책을 적용한다.

- 일반 게시글: 기존 공개·익명 정책 유지
- 중고장터 글: 로그인 회원만 조회·작성
- 중고장터 글: 익명 댓글 금지
- 중고장터 글: 작성 회원만 수정, 작성 회원 또는 관리자만 삭제

댓글 목록, 대댓글 분리 조회, 작성, 수정, 삭제 모든 경로에 같은 판정을 적용한다.

## 5. 연락처와 개인정보

### 5.1. 수집 범위

판매자가 선택한 카카오톡 ID, 전화번호, 이메일 등을 하나의 자유 입력 문자열로 받는다. 서비스는 연락 수단의 종류, 소유자, 실제 사용 가능 여부를 확인하지 않는다.

### 5.2. 노출 범위

- 목록 응답에는 연락처를 포함하지 않는다.
- 로그인 회원의 상세 응답에만 포함한다.
- 판매자 프로필에서는 닉네임과 프로필 이미지만 제공한다.
- 이메일, 출발 지역, 가입 정보, 내부 회원 ID는 노출하지 않는다.

### 5.3. 저장과 출력

- 앞뒤 공백을 제거한 1~30자 문자열로 저장한다.
- HTML로 해석하지 않고 텍스트로 출력한다.
- 연락처를 애플리케이션 로그, 접근 로그, 오류 메시지에 남기지 않는다.
- DTO의 `toString()` 또는 Request body 전체 로깅을 금지한다.
- 상세 응답에는 `Cache-Control: private, no-store`를 적용한다.

자유 입력을 허용하더라도 서비스가 개인정보를 저장하고 전달한다는 사실은 달라지지 않는다. 개인정보 처리방침과 판매글 작성 화면에 공개 범위를 안내하는 문구가 필요하다. 정확한 법률 문구는 운영 정책 검토 대상으로 남긴다.

## 6. 입력 안전성

### 연락처

연락처는 문자열 형식을 검증하지 않지만 제어문자와 NUL은 거부한다. `<script>` 같은 문자열이 저장되더라도 HTML로 실행하지 않고 텍스트로 렌더링해야 한다.

### 제목·본문

제목과 연락처는 일반 텍스트다. `수리·하자 있음`도 별도 설명 필드를 두지 않고 필요한 내용은 판매자가 본문에 작성한다. 본문은 기존 게시글과 같은 Markdown 저장·Viewer 렌더링 방식을 사용한다. 링크, 이미지, HTML 허용 범위는 기존 Toast UI Viewer 정책을 따른다. `dangerouslySetInnerHTML`로 원문을 직접 출력하지 않는다.

### Enum과 상품 분류

Enum은 서버의 허용값과 정확히 일치해야 한다. 상품 분류는 클라이언트 표시명을 신뢰하지 않고 `market_category.code`로 조회한다.

## 7. CSRF와 세션

판매글 등록·수정·상태 변경·삭제, 댓글 명령, 이미지 업로드는 상태를 변경하므로 기존 CSRF 토큰 정책을 적용한다.

- 쿠키: `XSRF-TOKEN`
- 요청 헤더: `X-XSRF-TOKEN`
- 세션 고정 방어: 로그인 시 `changeSessionId()`
- 쿠키 보안 속성: 기존 `HttpOnly`, `Secure`, `SameSite` 정책 유지

중고장터 기능을 편하게 호출하기 위해 CSRF 예외 경로를 추가하지 않는다.

## 8. 이미지 처리

### 8.1. 재사용 구조

중고장터는 기존 게시글 이미지 구조를 그대로 사용한다.

```text
Client
  → POST /api/v1/images
  → Backend 파일 검증
  → S3 비공개 버킷에 원본·썸네일 저장
  → CloudFront URL 반환
  → 판매글 등록 요청의 imageUrls에 포함
```

| 항목 | 정책 |
|---|---|
| 파일 개수 | 판매글당 0~5개 |
| 파일 크기 | 파일당 최대 5MB |
| 형식 | JPG, JPEG, PNG, WebP |
| 원본 | `public/posts/originals/` |
| 썸네일 | `public/posts/thumbnails/` |
| 썸네일 규격 | 최대 320×320, JPEG 품질 0.8 |
| DB 저장 | 원본 객체 키 또는 기존 호환 저장값 |
| 상세 | 원본 CloudFront URL |
| 목록 | 첫 이미지의 썸네일 CloudFront URL |

목록형과 앨범형 모두 같은 썸네일을 사용한다. 앨범형 때문에 별도 크기의 이미지를 추가 생성하지 않는다. 실제 화질이 부족한 경우 트래픽과 저장 비용을 측정한 뒤 앨범용 규격을 추가한다.

### 8.2. 공개 범위

S3 Block Public Access는 유지하므로 S3 직접 URL은 접근할 수 없다. CloudFront의 `public/posts/` 경로는 공개 조회이므로 URL을 아는 사용자는 로그인하지 않아도 이미지 파일만 열 수 있다.

이는 “중고장터의 목록·상세·연락처는 회원 전용”이라는 현재 요구에는 맞지만 “사진 바이트도 회원만 볼 수 있어야 한다”는 요구에는 맞지 않는다. 후자의 요구가 생기면 다음 대안을 비교한다.

- 별도 private prefix + CloudFront Signed URL
- 별도 private prefix + CloudFront Signed Cookie
- 백엔드 권한 확인 후 짧은 만료 URL 발급

현재는 기존 구조 재사용과 구현 속도를 우선한다.

### 8.3. URL 신뢰 경계

판매글 요청의 `imageUrls`에 외부 사이트 URL을 그대로 허용하면 추적 픽셀, 혼합 콘텐츠, 허용되지 않은 파일이 들어올 수 있다. 서버는 다음 조건을 확인한다.

- 설정된 CloudFront host와 일치
- 허용된 `public/posts/originals/` 경로
- URL 또는 객체 키 중복 없음
- 최대 5개

가능하면 URL 전체보다 업로드 응답의 `imageKey`만 판매글 요청에 보내는 편이 안전하다. 다만 사용자가 이미지 계약 결정을 후속으로 미뤘으므로 1차 구현은 기존 게시글의 `imageUrls` 계약을 그대로 사용한다. `imageKey` 전환은 이미지 파이프라인을 다시 다룰 때 결정한다.

### 8.4. 고아 이미지

이미지 업로드 후 판매글 등록을 취소하거나 이미지 목록에서 제거하면 S3 객체가 남는다. 지금 구조에는 업로드 소유권과 연결 상태를 기록하는 테이블이 없어 즉시 안전하게 삭제하기 어렵다.

1차 구현에서는 기존 게시글과 같은 동작을 유지한다. 후속 개선안은 다음과 같다.

1. `temporary/` prefix로 업로드
2. 판매글 저장 성공 시 최종 prefix로 승격
3. 일정 시간이 지난 미연결 임시 객체 자동 삭제

S3 Lifecycle만으로 `public/posts/` 전체를 지우면 정상 이미지도 삭제될 수 있으므로 적용하지 않는다.

## 9. 캐시와 검색 노출

- 판매글 목록·상세 JSON은 공유 CDN 캐시 대상에서 제외한다.
- 홈 공개 미리보기 응답에는 썸네일 URL과 publicId 외의 필드를 추가하지 않는다.
- 연락처가 포함된 상세 응답은 `private, no-store`로 반환한다.
- 로그인 전용 페이지에는 검색엔진 색인 방지 메타데이터를 적용한다.
- 서버 렌더링 과정에서 비로그인 사용자에게 판매글 데이터가 포함된 HTML을 보내지 않는다.
- 프런트엔드 route guard만 믿지 않고 API 응답을 기준으로 보호한다.

## 10. 관리자 조치

관리자는 `NORMAL`, `HIDDEN`, `BLOCKED` 운영 상태를 변경할 수 있고 별도 DELETE 요청으로 판매글을 삭제할 수 있다. 신고 기능은 만들지 않는다.

관리자 조치 사유와 변경 전후 상태를 별도 감사 테이블에 저장하는 것이 바람직하지만, 현재 관리자 도메인이 없으므로 1차 구현에 억지로 포함하지 않는다. 관리자 기능을 시작할 때 공통 moderation audit 구조로 설계한다.

## 11. 실패와 정보 노출

- 없는 글과 일반 회원이 볼 수 없는 숨김·차단·삭제 글은 모두 `404`로 응답한다.
- 다른 회원의 수정·삭제는 `403`으로 응답한다.
- 낙관적 락 충돌은 `409`로 응답하되 현재 판매글 내용이나 연락처를 오류 본문에 넣지 않는다.
- 파일 검증 실패 시 객체 키와 내부 S3 오류를 사용자 응답에 노출하지 않는다.
- 예외 메시지 문자열 비교를 사용하지 않고 `ErrorCode`와 타입 기반 예외를 사용한다.

## 12. 트레이드오프

현재 정책은 개발 속도와 기존 이미지 파이프라인 재사용을 우선한다. 그 대가로 이미지 URL 단독 접근, 고아 객체, 연락처 자유 입력에 따른 개인정보 노출 가능성이 남는다.

이를 다음 경계로 관리한다.

- 거래 데이터와 연락처는 인증 API로 보호
- 목록에는 연락처 미포함
- S3 직접 접근 차단
- 외부 이미지 URL 차단
- 로그에 연락처 미기록
- 이미지 바이트 보호가 필요해지면 Signed URL/Cookie로 전환
- 고아 객체 규모를 측정한 뒤 임시 업로드 구조 도입

## 13. 재검토 조건

- 이미지 URL이 외부에 공유되는 문제가 운영에서 확인되는 경우
- 연락처 크롤링이나 스팸이 발생하는 경우
- 신고·제재 이력에 대한 운영 요구가 생기는 경우
- 판매글을 검색엔진에 공개하려는 경우
- 쪽지 기능이 도입되어 연락처 직접 노출을 줄일 수 있는 경우
