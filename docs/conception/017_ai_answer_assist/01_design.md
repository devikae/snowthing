# 권한·변경 반영 MCP 기반 AI 검색·답변 보조 설계

- 상태: 0단계 완료 — 요약·검색 지원으로 범위 축소 (§6)
- 기준일: 2026-11-04 (KST)
- Linear: IKA-5 (부모), IKA-6 ~ IKA-13 (단계별 하위)
- 관련 설계: `docs/conception/009_mcp_bot/01_user-delegation-security.md`

## 1. 목표와 가설

검색 품질, 변경 데이터 정합성, 접근 권한을 함께 다루는 AI 검색·답변 보조를 만든다. 첫 사례는 미답변 질문에 대한 근거 있는 답변 초안이고, 일일 요약은 보조 기능이다.

가설: "질문 게시판의 질문 중 상당수는 과거 글·댓글에 답이 있는데도 반복되고, 운영자가 같은 답을 다시 쓰는 비용이 생긴다."

이 가설은 검증하지 않았다. 2026-11-03 운영 읽기 전용 조회(`docs/conception/012_profile_settings/06_production_image_inspection.json`)에서 소프트 삭제를 포함한 전체 게시글이 86개였다. 따라서 문제 규모가 작을 가능성이 높다고 보고, 0단계 조사 결과로 범위를 정한다. 문제가 작으면 요약·검색 지원으로 줄인다.

## 3. 착수 전 결정 (사용자 지시로 질문 없이 기본안 기준 결정)

사용자가 이번 작업에서는 착수 전 사항을 묻지 말고 진행하라고 지시했다(2026-11-04). 아래는 초안의 기본안(개인용 로컬 MCP, 실제 권한 정책, 키워드 기준선, 검토 후 게시, 자동 게시 꺼짐)을 기준으로 내린 결정이다. 각 결정은 해당 단계 계획에서 사용자가 뒤집을 수 있다.

### D1. 첫 사용자와 실행 위치

- 결정: 첫 사용자는 운영자(ROLE_ADMIN) 본인. 추론은 로컬 Codex + Skill, 연결은 로컬 STDIO MCP. 서버는 인덱싱·권한·원문·근거 버전 검증만 맡는다.
- 이유: 초안 기본안과 같다. 서버에 LLM 호출 비용과 키 관리가 생기지 않는다.
- 다른 선택지: 라이브톡 봇처럼 서버 내장 실행. 공개 브로드캐스트·비용·남용 대응이 필요해 지금 단계에는 과하다.

### D2. 0단계 판정 기준 (데이터를 보기 전에 고정)

데이터를 본 뒤 기준을 맞추는 일을 막기 위해 먼저 적는다.

- 조사 기간: 전체 기간과 최근 90일(KST)을 함께 본다.
- "답변"의 정의: 질문 작성자가 아닌 사람이 남긴 삭제되지 않은 댓글. 익명·비회원 댓글은 작성자 구분이 안 되므로 질문 작성자가 회원이고 댓글이 비회원일 때만 다른 사람으로 센다. 둘 다 비회원이면 판정 불가로 따로 센다.
- 답변 보조(초안) 진행 조건: 아래를 모두 만족.
  1. 최근 90일 공개 QNA 질문 30건 이상
  2. 다음 중 하나: 24시간 안에 답변이 없는 질문 비율 20% 이상, 또는 사람 검토로 확인한 반복 질문 사례 5건 이상
- 만족하지 못하면: 답변 초안·게시(4단계)는 보류하고 요약·검색 지원(1단계 검색 + 5단계 요약)으로 줄인다.
- 30, 20%, 5건은 근거가 있는 업계 기준이 아니라, 평가 표본이 30건보다 작으면 비율 지표를 의미 있게 말하기 어렵다는 점과 운영자가 체감할 최소 규모를 가정한 값이다. 이 한계를 결과와 함께 적는다.

### D3. 키워드 기준선 저장소

- 결정: 새 `search_document` 테이블에 게시글 구간·댓글을 넣고 MySQL FULLTEXT `WITH PARSER ngram`(토큰 2) 인덱스를 둔다. 1단계는 전체 재구축만, 2단계에서 outbox 증분 갱신을 붙인다.
- 이유: 새 인프라가 없다. 1단계와 2단계 이후가 같은 문서 집합을 쓰므로 기준선과 개선 결과를 같은 조건에서 비교할 수 있다.
- 다른 선택지
  - 원문 테이블에 바로 FULLTEXT: 단순하지만 구간·근거 버전·인덱싱 시각을 담을 곳이 없고, 원문 테이블 스키마가 검색 요구에 묶인다.
  - OpenSearch: 한국어 분석기 품질은 낫지만 운영 비용과 동기화 대상이 하나 늘어난다. 게시글 86개 규모에는 과하다.
- 부작용: ngram은 색인 크기가 커지고 짧은 단어 오탐이 늘어난다. 규모가 작아 지금은 문제가 되지 않지만 측정 대상에 넣는다.

### D4. 근거 단위와 근거 필드

- 게시글: 제목 1구간 + 본문을 문단 기준 최대 약 800자 구간으로 나눈다. 댓글: 댓글 1건 = 1구간(최대 1,000자), 부모 게시글 ID와 부모 댓글 ID를 함께 저장한다.
- 근거 필드: `evidence_id`(`{P|C}:{원문 ID}:{구간 번호}`), 원문 종류·ID, `source_version`, 구간 번호, 구간 해시(SHA-256), URL, 작성·수정·인덱싱 시각, 짧은 발췌(최대 200자).
- `evidence_id`는 권한을 대체하지 않는다. `get_evidence`는 매번 원문을 다시 읽고 공개 범위를 다시 검사한다.
- 검색 점수는 순위에만 쓰고 신뢰도로 반환하지 않는다.

### D5. 원문 버전

- 결정: 댓글은 기존 `version`(@Version)을 쓴다. 게시글은 `content_version BIGINT NOT NULL DEFAULT 0`을 추가해 제목·본문·카테고리·상태·삭제 변경 시 서비스에서 1 올린다(2단계).
- 이유: 게시글에 `@Version`을 붙이면 기존 비관적 락 경로와 조회수·반응 수 갱신 경로의 동작이 바뀔 수 있다. 검색에 필요한 것은 "내용 버전"이지 낙관적 락이 아니다.
- 다른 선택지: `updated_at`을 버전으로 사용. 시계 역행·같은 시각 두 번 수정에서 단조 증가를 보장하지 못한다.

### D6. 정합성

- 원문 DB가 기준이고 인덱스는 비동기 복제본이다.
- outbox 이벤트는 원문 변경과 같은 트랜잭션에 쓴다. 최소 1회 전달을 전제로 처리기를 멱등하게 만든다. 문서별 마지막 적용 버전보다 오래된 이벤트는 버린다. 삭제는 원문을 보관하지 않는 tombstone(ID·버전·삭제 시각)으로 남겨 역순 이벤트가 문서를 되살리지 못하게 한다.
- 처리기는 단일 인스턴스 폴링으로 시작하고 `market_thumbnail`과 같은 `due_at`/`lease_until`/`attempts` 패턴을 쓴다. 제한 재시도 후 영구 실패로 분리하고 재처리 API를 둔다. 주기적 대조와 체크포인트·롤백 가능한 무중단 재인덱싱(새 세대 생성 후 전환)을 둔다.
- 다른 선택지: `@TransactionalEventListener(AFTER_COMMIT)` + 비동기 처리. 커밋 후 프로세스가 죽으면 이벤트가 사라진다. Debezium·Kafka는 초안에서 제외했다.

### D7. 인증·권한

- 1단계(로컬 검증): 기존 STDIO 세션 방식을 그대로 쓰고 새 API는 관리자 전용으로 둔다.
- 4단계: 회원에 결합된 제한 API 토큰(`api_token`: 해시만 저장, 접두사, scope `snowthing:read`/`snowthing:draft` 분리, 최대 30일 만료, 폐기 가능, 마지막 사용 시각). 라이브톡 60초 위임 토큰은 재사용하지 않는다. 로컬에서는 OS 보안 저장소(Windows 자격 증명 관리자)를 우선하고 환경 변수는 개발용으로만 둔다.
- 권한 필터는 후보 생성 쿼리에서 적용하고, 발췌 반환과 모델 입력 전에 원문 기준으로 다시 검사한다. 캐시를 둘 경우 키에 권한 집합·권한 버전·조건·인덱스 세대를 넣는다(1단계는 캐시 없음).
- 게시는 초안 작성자의 권한으로 한다. 실제 사람이 검토 UI에서 승인한 기록만 인정하고, 모델이 보낸 `confirmed=true`는 인정하지 않는다.

### D8. 평가 자료 보관

- 저장소(devikae/snowthing)가 공개 저장소이므로 운영 원문이 들어간 평가 자료는 커밋하지 않는다. 형식·실행기·집계 결과만 커밋하고 원문 자료는 저장소 밖 로컬 경로에 둔다.

## 5. 0단계 조사 방법

- 스크립트: `scripts/inspect-qna-demand.py`. 기존 `scripts/inspect-image-cleanup.py`와 같이 EC2 역할과 SSM으로 운영 DB에 읽기 전용 SELECT만 실행한다. 쿼리마다 `MAX_EXECUTION_TIME=5000`을 둔다.
- 반환값은 집계 숫자뿐이다. 제목·본문·댓글 원문, 회원 ID·닉네임, 게시글 ID 목록은 반환하지 않는다.
- 측정 항목
  - 공개 게시글 수(카테고리별), 그중 QNA 비중
  - QNA 질문 수: 전체·최근 90일, 월별
  - 다른 사람의 답변이 있는 질문 수, 24시간 안에 답변된 질문 수, 답변이 없는 질문 수, 판정 불가 수
  - 첫 답변 소요 시간(분) P50·P90·최대
  - 운영자(ROLE_ADMIN)가 첫 답변을 단 질문 수
- 반복 질문은 SQL로 판정할 수 없다. 공개 QNA 게시판을 사람이 보고 "이전 글·댓글로 답할 수 있었던 질문"을 표시한다. 이 작업은 사용자 협조가 필요하다.
- `post.created_at`·`comment.created_at`은 KST `LocalDateTime`으로 저장되므로(JDBC `serverTimezone=Asia/Seoul`) 최근 90일 경계는 KST 기준 `NOW()`가 아니라 스크립트가 넘기는 KST 시각으로 계산한다.

- 로컬 검증(2026-11-04): 로컬 MySQL 8.0에 `001_initial_schema.sql`로 임시 스키마를 만들고 결과를 미리 계산한 게시글 9개·댓글 8개를 넣어 실행했다. 본인 댓글 제외, 삭제 댓글 제외, 삭제·숨김 글 제외, 비회원끼리 판정 불가, 24시간 미경과 제외, 90일 경계, 운영자 첫 답변, 카테고리·월별 집계가 모두 기대값과 같았다. `SET SESSION TRANSACTION READ ONLY` 상태에서 DELETE가 `ERROR 1792`로 거부되는 것도 확인했다. 임시 스키마는 삭제했다. CodeRabbit 지적 반영 후 MARKET 게시글과 "비회원이 먼저 답하고 운영자가 나중에 답한 질문"을 추가해 다시 실행했고, 카테고리 집계에서 MARKET이 빠지고 운영자 첫 답변으로 세지 않는 것을 확인했다.

## 6. 0단계 결과

- 측정: 2026-11-04 01:44:02 KST, 운영 DB 읽기 전용 집계(`02_stage0_demand.json`). 사용자가 직접 실행했다.
- 실행한 스크립트는 커밋 `50f124d` 버전이다. 이후 CodeRabbit 지적으로 두 쿼리를 고쳤지만 이 결과의 해석은 바뀌지 않는다.
  - `publicPostsByCategory`에 MARKET 2건이 포함되어 있다. 아래 공개 게시글 수는 MARKET을 뺀 값이다.
  - 운영자 첫 답변 쿼리는 비회원 답변을 건너뛰어 개수를 부풀릴 수 있었다. 부풀리는 쪽으로만 틀리는데 결과가 0이었으므로 실제 값도 0이다.

| 항목 | 값 |
|---|---|
| 공개 게시글 (MARKET 제외) | 81 (ANONYMOUS 33, FREE 30, QNA 17, FOOD 1) |
| QNA 비중 | 17 / 81 |
| QNA 월별 | 2026-10: 12, 2026-11: 5 (첫 QNA가 2026-10이라 전체 기간 = 최근 90일) |
| 다른 사람의 답변이 있는 질문 | 17 / 17 |
| 24시간 안에 답변 없는 질문 | 0 / 17 |
| 첫 답변 소요 시간 | P50 17분, P90 18분, 최대 18분 (n=17) |
| 운영자 첫 답변 | 0 |
| 판정 불가(비회원끼리) | 0 |

- 관찰: 17건 모두 17~18분 안에 첫 답변이 달렸다. 실제 사용자 활동이라면 드문 분포라서 초기 시드 글이거나 같은 사람이 일괄 작성했을 가능성이 있다. 이 집계는 원문과 작성자를 보지 않으므로 어느 쪽인지 판단할 수 없고, 사용자 확인이 필요하다. 어느 쪽이든 아래 판정은 같다.
- 판정 (D2): 최근 90일 QNA 17건으로 조건 1(30건 이상)을 만족하지 못하고, 24시간 미답변도 0건이다. **답변 보조(초안·승인 게시, IKA-12)는 보류하고 요약·검색 지원으로 범위를 줄인다.**
  - 진행: 1단계 키워드 검색·근거 조회(IKA-7, IKA-8), 2단계 정합성(IKA-10), 5단계 요약(IKA-13).
  - 보류: IKA-12. QNA가 90일 30건 이상으로 늘면 같은 스크립트로 다시 판정한다.
  - 평가(IKA-9): 실제 질문이 17건뿐이라 Recall@k를 비율로 보고하지 않고 n/N으로만 쓴다. 의미 검색(IKA-11)은 이 표본으로 개선을 입증하기 어려워, 기준선 측정 뒤 필요성을 다시 판단한다.
- 반복 질문 사례는 사람 검토가 필요한 항목이지만, 위 조건 1을 이미 만족하지 못해 판정에 영향이 없으므로 이번에는 요청하지 않는다.
