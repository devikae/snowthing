# Sprint 06 구조와 운영 절차

## 현재 구조

```text
브라우저
  → Cloudflare DNS·프록시·HTTPS
  → EC2 보안 그룹
  → 호스트 Nginx
      ├─ 화면 요청 → 127.0.0.1:3000 프런트 컨테이너
      └─ /api 요청 → 127.0.0.1:8080 백엔드 컨테이너
                         ├─ RDS MySQL
                         └─ EC2 IAM Role → 비공개 S3 업로드

브라우저 이미지 조회
  → images.snowthing.org
  → CloudFront HTTPS·캐시
  → OAC 서명
  → 비공개 S3

GitHub Actions
  → OIDC로 AWS 배포 역할 수임
  → 프런트·백엔드 이미지 빌드
  → ECR에 candidate-<SHA> push
  → digest 조회
  → SSM Run Command
  → EC2가 digest 이미지 pull·실행
```

이전에는 EC2가 Git 소스를 받은 뒤 `docker compose up --build`로 직접 빌드했습니다. 지금은 GitHub Actions가 한 번 빌드한 이미지를 ECR에 보관하고, EC2는 그 결과물만 실행합니다. 서버 사양과 캐시 상태에 따라 빌드 결과가 달라지는 문제를 줄였고, 실행했던 바이너리와 되돌릴 바이너리를 digest로 구분할 수 있게 됐습니다.

## 주요 설정 키

### GitHub Actions Variables

- `AWS_DEPLOY_ROLE_ARN`: OIDC로 수임할 GitHub 배포 역할 ARN
- `AWS_REGION`: `ap-northeast-2`
- `EC2_INSTANCE_ID`: SSM 명령을 받을 운영 EC2 ID
- `ECR_BACKEND_REPOSITORY`: `snowthing/backend`
- `ECR_FRONTEND_REPOSITORY`: `snowthing/frontend`
- `NEXT_PUBLIC_API_BASE_URL`: `https://snowthing.org`

### EC2 운영 환경

- `SNOWTHING_IMAGE_BASE_URL`: `https://images.snowthing.org`
- `SNOWTHING_S3_BUCKET`: 이미지 원본·썸네일을 저장할 비공개 버킷 이름

비밀번호가 아닌 저장소 이름과 리전은 Variables에 둡니다. DB 비밀번호처럼 노출되면 안 되는 값은 GitHub 변수나 이미지에 넣지 않고 EC2의 `/etc/snowthing/prod.env`에서 관리합니다.

### IAM 역할

- GitHub 역할: 두 ECR 저장소에 대한 push·조회·태그 삭제, 대상 EC2에 대한 SSM 명령 전송과 결과 조회
- EC2 역할: 두 ECR 저장소 pull, 필요한 S3 경로 접근, SSM Agent 통신

`ecr:GetAuthorizationToken`은 리소스 ARN으로 제한할 수 없어 `Resource: "*"`를 사용합니다. 이미지 작업 권한은 `snowthing/backend`, `snowthing/frontend` ARN으로 제한합니다.

### 이미지 IAM과 CloudFront

- EC2 Role: 지정 S3 버킷의 업로드에 필요한 객체 권한만 사용하며 장기 Access Key를 컨테이너에 넣지 않습니다.
- CloudFront OAC: 지정 CloudFront 배포가 비공개 S3 객체를 읽을 수 있게 버킷 정책에서 허용합니다.
- 일반 Client: S3 권한이 없으며 CloudFront URL만 사용합니다.
- S3 Block Public Access: 계속 활성화합니다.

CloudFront 사용자 인증서는 서비스 특성상 `us-east-1` ACM에서 관리합니다. 실제 S3와 EC2가 서울 리전에 있어도 CloudFront에 연결하는 ACM 인증서는 버지니아 북부 리전에 있어야 합니다. DNS의 `images.snowthing.org`는 CloudFront 배포 도메인을 가리킵니다.

## 이미지 업로드·조회 절차

1. 로그인한 Client가 CSRF 토큰과 함께 이미지 업로드 API를 호출합니다.
2. 백엔드는 5MB 제한, JPG·PNG·WebP MIME과 파일 시그니처를 확인합니다.
3. 원본은 `public/posts/originals/{UUID}.{확장자}`에 저장합니다.
4. 최대 320×320 JPEG 품질 0.8 썸네일을 `public/posts/thumbnails/{UUID}.jpg`에 저장합니다.
5. DB에는 원본 객체 키를 저장합니다.
6. 상세 API는 원본 URL을, 목록 API는 썸네일 URL을 반환합니다.
7. Client는 EC2를 거치지 않고 CloudFront에서 이미지를 받습니다.

객체 키는 UUID이므로 `Cache-Control: public, max-age=31536000, immutable`을 적용합니다. 같은 키의 내용을 덮어쓰면 CloudFront 캐시와 원본이 달라질 수 있으므로 이미지 변경 시 새 UUID를 사용합니다.

CloudFront와 S3는 요청 수·전송량·저장량에 따라 비용이 발생합니다. 썸네일 객체 때문에 저장 객체 수는 늘지만 목록에서 원본을 반복 전송하지 않아 조회 전송량을 줄일 수 있습니다. 정확한 비용은 운영 트래픽과 AWS 요금표를 기준으로 확인합니다.

공개 게시글 경로를 회원 전용 이미지에 재사용하지 않습니다. 이후 중고장터 이미지는 별도 prefix와 캐시 동작을 만들고, 권한 확인 뒤 CloudFront Signed URL/Cookie를 발급하는 방식을 검토합니다.

## ECR 태그와 보관 정책

- `candidate-<SHA>`: 배포 전 후보. 7일 후 만료
- `release-<SHA>`: 배포와 헬스체크가 끝난 버전. 최근 3개 보관
- `stable-<SHA>`: 장기 복구 기준. 최근 1개 보관
- 태그 없는 이미지: 1일 후 만료

candidate와 release 태그를 한 이미지에 계속 같이 두면 candidate 7일 규칙이 release 이미지까지 만료시킬 수 있습니다. 그래서 배포 성공 후 release 태그를 만든 다음 candidate 태그를 제거합니다. stable로 옮길 때도 같은 digest에 남은 release 태그가 없는지 확인해야 합니다.

## 비용

ECR private 저장소는 저장 용량 기준으로 과금됩니다. 서울 리전의 정확한 금액은 결제 시점의 AWS 요금표로 다시 확인해야 하지만, 작업 당시 계산에는 약 USD 0.10/GB-월을 사용했습니다. 5GB면 약 USD 0.50/월, 10GB면 약 USD 1/월 수준이며 세금과 환율은 별도입니다. 같은 리전의 ECR에서 EC2로 이미지를 받는 데이터 전송은 별도 인터넷 다운로드보다 유리하지만, 스캔 기능이나 리전 간 전송을 추가하면 비용이 달라질 수 있습니다.

## 정상 배포 절차

1. 백엔드는 Spotless와 테스트, 프런트는 `npm run build`를 통과해야 합니다.
2. Actions가 `candidate-<전체 커밋 SHA>` 이미지를 만듭니다.
3. ECR push 후 digest를 조회합니다.
4. SSM으로 `저장소@sha256:...` 주소를 EC2에 전달합니다.
5. EC2가 ECR에 로그인하고 해당 digest를 pull합니다.
6. Compose가 대상 서비스 하나만 `--no-build`로 교체합니다.
7. 프런트는 3000번, 백엔드는 8080번 로컬 주소로 헬스체크합니다.
8. 성공하면 release 태그를 만들고 candidate 태그를 지웁니다.
9. 실패하면 배포 전에 실행 중이던 이미지 주소로 컨테이너를 다시 올립니다.

## 수동 롤백 절차

1. ECR에서 되돌릴 `release-<SHA>` 또는 `stable-<SHA>`를 고릅니다.
2. GitHub Actions의 `Deploy Frontend` 수동 실행에서 `rollback_tag`를 입력합니다.
3. Actions가 태그를 digest로 바꾼 뒤 SSM으로 전달합니다.
4. EC2가 선택한 digest로 컨테이너를 교체하고 헬스체크합니다.
5. 외부 HTTPS에서 화면과 API를 확인합니다.
6. DB 스키마 변경이 포함된 버전이라면 이미지부터 바꾸지 말고 이전 앱과 현재 스키마의 호환성을 먼저 확인합니다.

## 백업·복구와 자원 정리

- 이미지 롤백은 애플리케이션 실행 파일만 되돌립니다. RDS 데이터는 되돌리지 않습니다.
- DB 복구는 운영 RDS를 덮어쓰지 않고 새 DB로 복원해야 합니다.
- 복원 검증 앱은 운영 DB와 S3에 쓰기 권한을 가지면 안 됩니다.
- 검증이 끝난 임시 DB와 사용하지 않는 스냅샷은 승인된 보존 기간에 따라 정리합니다.
- EC2, EBS, 공인 IPv4, RDS, 백업, S3, ECR 비용을 함께 확인합니다. Budgets 알림은 자동 결제 차단 기능이 아닙니다.

### 실제로 수행한 RDS 복원 검증

1. 운영 DB에서 스냅샷 기준 행 두 개를 조회했습니다.
2. 수동 스냅샷을 만든 뒤 운영 DB에 비교용 행을 하나 더 추가했습니다.
3. 운영 DB를 수정하지 않고 스냅샷을 새 DB 인스턴스 `snowthing-db-restore-test`로 복원했습니다.
4. 복원 DB에서 같은 조회문을 실행했습니다.
5. 기준 행 두 개는 존재하고 스냅샷 이후 행은 존재하지 않는 것을 확인했습니다.

이 검증으로 확인한 것은 스냅샷의 시점 일관성과 별도 DB 복원입니다. SQL 클라이언트의 별도 연결도 확인했습니다. 반면 복원 DB 전용 읽기 계정, 애플리케이션의 복원 DB 엔드포인트 연결, 운영 DB·S3 쓰기 차단은 제공된 화면만으로 입증되지 않습니다. 해당 항목을 미션 완료 증거로 내야 한다면 읽기 전용 계정으로 검증 앱을 실행하고 쓰기 거부 결과까지 추가해야 합니다.

복원 검증이 끝나면 다음 순서로 정리합니다.

1. 제출에 쓸 쿼리 결과와 시각을 보존합니다.
2. 복원 DB가 운영 트래픽에 연결되지 않았는지 다시 확인합니다.
3. 보존 승인을 받은 스냅샷만 남깁니다.
4. `snowthing-db-restore-test`를 삭제하고 RDS 목록에서 제거됐는지 확인합니다.
5. 최종 스냅샷 비용과 복원 DB가 실행된 시간을 비용 기록에 반영합니다.

## 배포 산출물과 배포 설정을 같은 커밋으로 맞추는 절차

현재 배포 단위는 이미지 digest 하나만이 아니라 `Git commit SHA + image digest`의 묶음입니다. SHA는 소스와 `compose.prod.yml`·배포 스크립트를 식별하고, digest는 실제 실행할 이미지 내용을 식별합니다.

1. Actions가 워크플로를 시작한 `${{ github.sha }}`의 소스를 checkout합니다.
2. 그 소스로 이미지를 빌드해 ECR에 push하고 digest를 조회합니다.
3. SSM에 image URI와 함께 같은 `${{ github.sha }}`를 전달합니다.
4. EC2는 `git fetch origin <SHA>` 후 `git reset --hard <SHA>`를 수행합니다.
5. `git rev-parse HEAD`가 전달받은 SHA와 다르면 배포를 중단합니다.
6. 일치할 때만 해당 커밋의 Compose와 배포 스크립트로 digest 이미지를 실행합니다.
7. 롤백은 `release/stable` 태그에서 원본 SHA와 digest를 함께 복원합니다.

브랜치 HEAD는 새 push가 들어오면 이동합니다. Actions가 대기하는 동안 새 커밋이 들어오면, 이전 구조에서는 검증한 이미지와 EC2가 받은 배포 파일이 서로 다른 버전이 될 수 있었습니다. 정확한 SHA를 전달하면 브랜치가 이동해도 배포 작업의 입력은 변하지 않습니다.

`reset --hard`는 `/home/ubuntu/snowthing` 작업 트리의 추적 파일을 해당 커밋 상태로 맞춥니다. 운영 비밀값은 저장소 밖 `/etc/snowthing/prod.env`에 있으므로 영향을 받지 않습니다. 대신 서버에서 저장소의 추적 파일을 직접 고치면 다음 배포 때 사라지므로, 운영 변경은 Git으로 관리해야 합니다. 배포 동시성은 프런트와 백엔드가 같은 EC2 작업 트리를 동시에 reset하지 않도록 공유 concurrency로 직렬화합니다.

대안은 Compose와 스크립트를 별도 release artifact로 묶거나 이미지 안에 배포 메타데이터를 포함하는 방식입니다. 별도 artifact는 Git checkout 의존성을 줄이지만 artifact 저장·서명·보존 절차가 추가됩니다. 현재 단일 EC2 구성에서는 commit SHA를 직접 checkout하고 digest를 고정하는 방식이 가장 단순하면서도 추적성을 확보합니다.

## 이미지 업로드 요청 크기 제한

애플리케이션이 허용하는 이미지 파일 크기는 최대 5MB입니다. Spring multipart 파서가 서비스 검증보다 먼저 요청을 거부하지 않도록 `spring.servlet.multipart.max-file-size`를 `5MB`로 맞췄습니다. multipart 경계와 각 파트의 헤더가 파일 외에 추가되므로 전체 요청 제한인 `max-request-size`는 `6MB`로 설정했습니다.

파서 단계에서 제한을 넘으면 `MaxUploadSizeExceededException`이 발생합니다. 이 예외도 서비스 검증과 같은 `400 FILE_SIZE_EXCEEDED` 응답으로 변환합니다. 운영 Nginx에는 `/etc/nginx/conf.d/snowthing-upload-limit.conf`를 배포 스크립트가 관리하며 `client_max_body_size 6m`을 적용합니다. 변경 시 `nginx -t`를 먼저 통과한 경우에만 reload하고, 검증에 실패하면 기존 설정을 복원합니다.

## stable 승격 시 태그 처리

`release-<SHA>`를 stable로 승격할 때는 사용자가 선택한 release 태그 하나만 제거합니다. 같은 digest에 여러 `release-*` 태그가 붙어 있어도 다른 커밋의 태그는 유지합니다. 서로 다른 커밋에서 결과 이미지가 우연히 같을 수 있으므로 digest가 같다는 이유만으로 롤백 지점을 일괄 삭제하지 않습니다. 전체 보관 개수와 기간은 ECR lifecycle 정책이 담당합니다.

## 장애 진단 로그 보안

배포 실패 시 컨테이너 로그와 Nginx 오류 로그 원문은 Actions나 SSM stdout으로 출력하지 않습니다. 원문은 EC2의 `/var/log/snowthing-deploy`에만 저장하며 디렉터리는 `0700`, 파일은 `0600`으로 제한합니다. Actions에는 파일 경로와 서비스명, 이미지 주소, 컨테이너 실행 상태·종료 코드·재시작 횟수만 출력합니다. 14일이 지난 진단 파일은 매 배포 시 삭제합니다.

## 운영 스키마 마이그레이션 경계

현재 운영 RDS는 `database/production/001_initial_schema.sql`과 `002_reference_data.sql`을 관리 계정으로 최초 한 번 적용했고, 애플리케이션 계정에는 DDL 권한을 주지 않았습니다. 따라서 애플리케이션 시작 시 Flyway를 자동 실행하도록 바꾸면 최소 권한 원칙이 깨집니다.

Sprint 05의 추천 카운터 CHECK 제약부터 다음 절차를 적용합니다.

1. 버전 SQL은 `database/production/NNN_migration_*.sql` 형식으로 관리합니다.
2. `scripts/run-production-migrations.sh`는 SHA-256 checksum과 적용 시각을 `schema_migration`에 기록합니다. 이미 적용한 파일의 checksum이 달라지면 즉시 실패합니다.
3. 백엔드 배포 job은 GitHub `production-migration` Environment 승인을 통과한 뒤, EC2에서 마이그레이션을 먼저 실행합니다. 마이그레이션 명령이 0이 아닌 종료 코드를 반환하면 같은 SSM 명령의 애플리케이션 배포 단계로 넘어가지 않습니다.
4. 실행 주체는 애플리케이션 계정이 아니라 전용 migration 계정입니다. 계정에는 대상 DB의 schema version 테이블 생성·기록, 대상 테이블 SELECT·UPDATE, ALTER, 이번 idempotent DDL에 필요한 routine 권한만 부여합니다. 애플리케이션 런타임에는 이 계정을 전달하지 않습니다.
5. EC2의 `/etc/snowthing/migration.env`는 root 전용 `0600`으로 만들고 아래 항목만 둡니다. 비밀번호 인증 대신 RDS IAM 인증을 기본 운영 방식으로 사용합니다.

```dotenv
SNOWTHING_MIGRATION_DB_HOST=<RDS endpoint>
SNOWTHING_MIGRATION_DB_PORT=3306
SNOWTHING_MIGRATION_DB_NAME=snowthing
SNOWTHING_MIGRATION_DB_USERNAME=snowthing_migrator
SNOWTHING_MIGRATION_DB_AUTH_MODE=iam
SNOWTHING_MIGRATION_DB_SSL_MODE=VERIFY_IDENTITY
SNOWTHING_MIGRATION_DB_SSL_CA=/path/to/rds-ca-bundle.pem
```

EC2에는 `mysql` client, `aws` CLI, `sha256sum`이 있어야 하며 EC2 역할에는 해당 migration DB user로 `rds-db:connect`할 권한만 추가합니다. GitHub Environment에는 필수 승인자를 지정해야 하며, 환경 이름만 생성하고 보호 규칙을 비워두면 승인 절차로 보지 않습니다.

`003_migration_post_reaction_count_checks.sql`은 `post_reaction`을 원본으로 불일치 카운터를 먼저 보정하고 두 CHECK를 추가합니다. 마이그레이션 전 RDS snapshot 상태와 불일치 건수를 확인하고, 적용 후에는 `SHOW CREATE TABLE`, 남은 불일치 0건, 음수 UPDATE 거부를 확인합니다. 실패 시 DB를 자동 역방향 변경하거나 이전 이미지를 자동 배포하지 않습니다. 원인을 확인한 뒤 forward fix를 적용하며, 복원이 필요하면 사전에 확인한 snapshot으로 별도 RDS를 복원해 검증합니다.

향후 호환되지 않는 변경은 `expand → 양쪽 앱 버전 공존 검증 → 데이터 이관 → contract` 순서로 나눕니다.
