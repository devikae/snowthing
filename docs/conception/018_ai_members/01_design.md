# AI 멤버 설계

- 상태: 설계 승인 (2026-11-04)
- 기준일: 2026-11-04 (KST)
- Linear: IKA-14
- 관련 설계: `docs/conception/009_mcp_bot/01_user-delegation-security.md`, `docs/conception/017_ai_answer_assist/01_design.md`

## 1. 목적과 범위

초반 리젠을 맡을 AI 멤버 4명을 둔다. 실제 사용자가 늘어 자연 리젠이 생기면 환경변수로 끈다.

| 포함 | 제외 |
|---|---|
| 자유게시판(FREE), 익명게시판(ANONYMOUS), 질문게시판(QNA) 글·댓글 | 장터, 카풀, 모집 게시판, 공지 |
| 라이브톡 채팅 | 쪽지, 반응(추천) |
| 실제 사용자 글에 대한 짧은 반응 | 실제 사용자와의 긴 대화 |
| 사이트 데이터 기반 소재 | 외부 커뮤니티 수집(크롤링) |

공개: 공지 게시판에 "초기 운영을 위해 AI 멤버가 함께 활동한다, 누구인지는 공개하지 않는다"는 글을 고정한다. 운영자가 직접 작성한다. 기능을 끌 때 공지도 함께 내리거나 종료를 알린다.

## 2. 캐릭터

- 4명. 실력, 관심사, 성향이 서로 부딪히도록 잡는다. 성격·사고방식·말투·관심 소재를 캐릭터마다 정의한다.
- 네 곳(자게·익게·질게·채팅)을 골고루 쓴다. 특정 게시판 전담은 없다.
- 의견이 갈리는 주제에서는 서로 반박하고 재반박한다(키배). 미리 짝을 정하지 않고 성향 차이로 생기게 한다.
- 공통 금지: 장터 글, 연락처·URL, 실존 인물 비방, 맛집·광고성 추천.
- 정보성 답변은 단정하지 않는 말투를 캐릭터 정의에 넣어 틀린 정보의 위험을 줄인다.
- 캐릭터 상세 정의는 저장소 밖 페르소나 파일에만 둔다(§3). 저장소가 공개이므로 이 문서에도 적지 않는다.

## 3. 계정과 설정

- 계정: 일반 `member` 4개. 이메일 `ai-agent01@snowthing.invalid` ~ `ai-agent04@snowthing.invalid`, `ROLE_USER`, `ACTIVE`.
  - `.invalid`는 RFC 2606 예약 도메인이라 메일이 실제로 나가지 않는다.
  - 이메일은 공개 응답에 나오지 않는다. 공개되는 값은 닉네임뿐이다.
  - 비밀번호는 NULL로 두어 로그인할 수 없게 한다.
  - 계정은 마이그레이션이 아니라 기동 시 `AiMemberBootstrap`이 페르소나 파일로 만든다(구현 계획 단계에서 031 시드안을 바꿈). 닉네임이 저장소·마이그레이션 이력에 남지 않고 운영 DB를 손으로 고칠 필요가 없다. 같은 닉네임을 다른 회원이 쓰면 그 캐릭터는 건너뛴다. 이미 있는 계정의 닉네임은 바꾸지 않는다.
- 스키마 변경·마이그레이션 없음. 별도 테이블을 두지 않는다.
- 페르소나 파일: YAML (`backend/ai-personas.example.yml` 형식). 운영은 호스트 `/opt/snowthing-ai/personas.yml`을 컨테이너 `/etc/snowthing-ai/personas.yml`로 읽기 전용 마운트한다(`compose.prod.yml`). 저장소에는 예시 파일만 둔다. 이메일은 `@snowthing.invalid`, IP는 공인 IPv4만 받고 하나라도 틀리면 파일 전체를 거부한다.
- ON/OFF: `SNOWTHING_AI_MEMBERS_ENABLED` (기본 false). 기존 `SNOWTHING_BOT_ENABLED`와 같은 방식이다.
- 익명 글 IP: 서버가 직접 쓰는 글은 `writerIp`가 비거나 서버 IP가 된다. 캐릭터마다 고정 가상 IP 앞자리를 페르소나 파일에 두고 사용한다. 실제 사용자 IP와 같은 앞자리를 쓰지 않도록 검사한다.
- 상태 저장 없음. 오늘 쓴 글·댓글 수, 실제 사용자와 주고받은 횟수는 `post`, `comment`를 작성자 기준으로 세어 구한다.

## 4. 스케줄 (Spring)

- 매일 0시(KST)에 그날 활동 시각을 메모리에서 랜덤으로 뽑는다.
  - 글: 캐릭터마다 0~5개. 전체 상한은 두지 않는다.
  - 채팅: 하루 5회, 몰려서 짧게 주고받는 대화.
  - 시간대: 07~09, 12~13, 18~20, 20~24시. 새벽에는 활동하지 않는다.
- 댓글: 새 글이 생기면 수십 분~수 시간 뒤 랜덤으로 붙인다. AI 글과 실제 사용자 글 모두 대상이다.
- 키배: 반박성 댓글이 달리면 상대 캐릭터가 확률적으로 재반박한다.
- 실제 사용자와의 대화: AI 댓글에 실제 사용자가 답글을 달면 1~2회까지만 이어가고 멈춘다.
- 채팅: 대화 한 번을 LLM 호출 한 번으로 3~6마디 생성하고 수십 초 간격으로 나눠 보낸다. 실제 사용자가 말을 걸면 가끔 짧게 반응한다.
- 서버 재시작: 오늘 이미 쓴 개수를 세어 남은 몫만 다시 뽑는다.
- 단일 인스턴스 기준이다. 다중 인스턴스가 되면 `market_thumbnail`의 `due_at`/`lease_until` 패턴으로 옮긴다.

## 5. 생성 (봇 서버)

- `snowthing-mcp-server`에 내부 API `POST /internal/v1/ai-members/compose`를 추가한다. 인증은 기존 `X-Snowthing-Internal-Secret`.
- 모델은 기존 `OPENAI_MODEL`, 유해성 검사는 기존 `omni-moderation-latest`를 쓴다.
- 입력: 페르소나, 행동 종류(글·댓글·채팅), 게시판, 대상 글·댓글 스레드, 사이트 데이터(날짜·시즌 시점, 최근 설질 제보, 리조트 목록), 최근 7일 제목, 선택 화제 키워드.
- 소재: "국내 스노보드 커뮤니티에서 흔한 주제" 분위기로 모델이 고른다. 외부 사이트를 수집하지 않는다.
- 쓰기는 Spring이 한다. 봇 서버에 쓰기 권한을 위임하지 않으므로 009의 읽기 전용 경계가 유지된다.

## 6. 안전장치

- 생성 결과에 moderation, 연락처·URL 검사(기존 봇 답변 필터 재사용), 길이 검사, 최근 글 중복 검사를 적용한다. 실패하면 버리고 로그만 남긴다.
- 하루 LLM 호출 상한 기본 100회. 예상 사용량은 하루 40~60회다. 기존 `request_budget_window` 패턴을 재사용한다.
- 봇 서버 장애 시 해당 행동은 건너뛰고 재시도하지 않는다.

## 7. 결정과 다른 선택지

| 결정 | 고른 것 | 다른 선택지와 버린 이유 |
|---|---|---|
| 실행 위치 | Spring 스케줄러 + 봇 서버 생성 | 봇 서버가 직접 글쓰기: 009 쓰기 위임 금지와 충돌 / 로컬 PC: PC가 꺼지면 멈추고 시간대가 몰림 |
| 게시 방식 | 자동 검사 후 바로 게시 | 검토 대기열: 승인 시점에 글이 몰려 랜덤성이 사라지고 관리자 화면이 필요 |
| 실제 사용자와의 상호작용 | 가끔 댓글, 대화 1~2회 | 끝까지 대화: 비용 증가, 캐릭터 붕괴 / AI끼리만: 리젠 효과 절반 |
| 소재 | 사이트 데이터 + 커뮤니티 분위기 지시 | 외부 커뮤니티 수집: 약관·저작권 위험, 원문과 겹쳐 들킴 / 뉴스 API: 봇 티, 저작권 |
| 설정 저장 | 저장소 밖 파일 + 환경변수 | `ai_persona` 테이블 또는 `member.is_ai`: 4명 규모에 과하고 응답 노출 위험 |

## 8. 범위 밖

- 날씨: 슬로프캠 기온 기능이 생기면 사이트 데이터 입력에 붙인다.
- 관리자 화면.
- 기능을 끈 뒤 계정 처리(유지·탈퇴). 끌 때 정한다.

## 9. 작업 단위

1. 봇 서버: compose API(`POST /internal/v1/ai-members/compose`, JSON 스키마 출력, moderation, 실패 시 422), 테스트
2. 백엔드: 설정·페르소나 로딩·기동 시 계정 연결, 하루 계획(`AiActivityPlanner`), 댓글 판단(`AiReactionPolicy`), 1분 주기 스케줄러, 실행 서비스, `ContactFilter` 분리, 테스트

### 구현 메모

- 계획·댓글 판단의 난수는 날짜·글·댓글·회원 ID로 시드를 정한다. 같은 대상에 대한 판단이 매 분 같으므로 상태를 저장하지 않아도 된다. 시드가 연속된 값이라 `java.util.Random`은 첫 난수가 거의 같아 모든 캐릭터가 똑같이 판단했다. 시드를 섞어 주는 `SplittableRandom`을 쓴다.
- 실패한 댓글 시도는 메모리에 기억해 같은 대상을 매 분 다시 호출하지 않는다(날이 바뀌면 비운다).
- compose 호출(최대 15초)은 전용 단일 스레드에서 돌린다. 공용 `@Scheduled` 스레드를 막지 않고 AI 행동이 한 번에 하나씩만 실행된다.
- 판단용 조회는 `AiMemberQueryRepository`(JDBC 읽기 전용)에 모았다. 기존 `PostRepository`·`CommentRepository`는 바꾸지 않는다.
- 실제 사람 닉네임은 봇 서버로 보내지 않는다. 다른 사람은 "회원N"·"비회원", AI는 페르소나 키로 부른다.

## 10. 리스크

- 매일 비슷한 패턴이면 티가 날 수 있어 랜덤 폭을 넓게 잡는다.
- 모델 단가를 확인하지 않았다. 호출 수 상한으로만 막고 첫 주 실제 비용을 확인한다.
- 생성 글이 사실과 다를 수 있다. 공지에 정보 재확인 안내를 넣는다.
