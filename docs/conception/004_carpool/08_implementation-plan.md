# 카풀 구현 현황과 후속 계획

아래 1~5단계의 초기 기능은 구현되었습니다. 현재 구현은 신청·매칭 시스템이 아니라 구조화된 모집글, 예상 비용, 댓글을 제공하는 범위입니다.

## 1단계: 문서·계약

- `CARPOOL` 카테고리와 Post 확장 규칙 확인
- `CarpoolDetail` ERD와 production migration 작성
- ErrorCode·요청/응답 DTO 계약 확정
- 오피넷·카카오모빌리티 환경변수와 timeout 정책 확정

## 2단계: 백엔드 도메인

- CarpoolDetail Entity와 Repository
- 카풀 생성·조회·수정·삭제 Service/Controller
- Post와 CarpoolDetail 동일 트랜잭션 처리
- 입력 검증과 연락처 노출 정책
- 비용 계산 순수 도메인 서비스

## 3단계: 외부 연동

- 오피넷 Client와 캐시
- 카카오모빌리티 Route Client
- 외부 장애 시 유효한 유가 캐시 사용, 캐시가 없으면 저장 중단 및 오류 응답
- 리조트별 검증 경로 좌표를 DB 마스터 데이터로 관리
- API 키·timeout·응답 매핑 테스트

## 4단계: 프런트엔드

- 카풀 목록·상세·작성·수정 화면
- 자동 계산·1인 금액 직접 지정 UI
- 댓글 연결
- 장비 적재 여부와 목록 20건 페이징
- 메인·사이드바 최신 4건 실제 데이터 연결
- 비로그인 작성 접근의 회원가입·로그인 유도
- 연락처 공개 동의 UI

## 5단계: 검증·배포

- 단위·통합·브라우저 테스트
- 빈 RDS migration 검증
- 운영 설정에 외부 API 키 주입
- 외부 HTTPS에서 게시글·댓글·계산·연락처 노출 검증
- `010` 마이그레이션의 목록 복합 인덱스와 13개 리조트 좌표 검증
- `011` 마이그레이션의 유가 출처·목적지 좌표 스냅샷과 수동 장애 폴백 검증
- `012` 마이그레이션의 최신순 정렬 인덱스와 목록 최대 100페이지 제한 검증

## 후속 운영 과제

- 다중 인스턴스로 확장하면 인메모리 호출 제한을 Redis 공용 카운터로 교체
- 운영 데이터가 늘면 목록 쿼리 `EXPLAIN ANALYZE` 결과에 따라 인덱스 순서 또는 조회 모델 재검토
- 리조트 진입 위치가 바뀌면 검증 후 새 마이그레이션으로 기준 좌표 갱신

구현 중 API 제공자의 실제 요청 형식이나 비용 정책이 설계와 다르면 코드를 먼저 바꾸지 않고 문서와 계약을 갱신한 뒤 진행합니다.
