# Sprint 4 댓글 조회 벤치마크 학습 정리

## 1. 왜 이 스프린트가 필요했나

댓글 기능은 데이터가 적을 때는 어떤 조회 방식도 비슷하게 보입니다. 하지만 게시글과 댓글이 늘어나면 같은 SQL도 읽어야 할 후보 행 수, 정렬 비용, 인덱스 선택이 달라집니다. 그래서 이번 스프린트는 기능 테스트가 아니라 **데이터 규모와 분포가 바뀌어도 댓글 조회 구조가 유지되는지**를 MySQL 8.0에서 확인하는 단계였습니다.

1천건은 기능·커서 누락 검증, 1만건은 실행계획 변화 관찰, 10만건은 선택도와 Hotspot 검증, 백만건은 선택 과제로 사용했습니다. 게시글 100개와 일반·중간·Hot post를 섞은 이유는 `post_id` 조건이 모든 행을 골라내는지, 특정 게시글 쏠림이 인덱스에 어떤 부담을 주는지 함께 보기 위해서입니다.

## 2. 핵심 개념

### 데이터 선택도(selectivity)

선택도는 조건이 전체 행 중 얼마만큼을 걸러내는지를 나타내는 정도입니다. `post_id = 특정 게시글`이 100만 행 중 2천 행만 찾으면 선택도가 높고(소수의 행을 선택), 모든 행의 절반을 찾으면 선택도가 낮습니다. MySQL 옵티마이저는 인덱스를 타서 읽을 행 수와 테이블 전체를 읽을 비용을 비교해 계획을 정합니다.

`post_id` 하나만 있는 것보다 `(post_id, parent_id, comment_id)` 복합 인덱스가 루트 댓글 조회에 유리한 이유는 게시글과 루트 여부를 함께 좁힐 수 있기 때문입니다. 반대로 Hot post처럼 한 게시글에 댓글이 몰리면 `post_id` 조건만으로는 후보가 많이 남아 선택도가 낮아지고, 정렬·추가 조건 비용이 커집니다.

### estimated rows와 actual rows

- `estimated rows`: 통계와 조건을 바탕으로 옵티마이저가 예상한 처리 행 수
- `actual rows`: `EXPLAIN ANALYZE` 실행 중 실제로 처리한 행 수

두 값의 차이는 통계가 오래됐거나, 컬럼 간 상관관계를 옵티마이저가 정확히 알기 어렵거나, 데이터가 Hotspot처럼 균일하지 않을 때 생깁니다. 차이가 크면 `ANALYZE TABLE`로 통계를 갱신하고, 필요하면 히스토그램·복합 인덱스·쿼리 조건을 검토합니다. 통계가 맞아도 실행 시점의 데이터 변화 때문에 차이는 남을 수 있습니다.

### Cursor pagination과 index seek

Cursor pagination은 “몇 번째 페이지”가 아니라 마지막으로 본 `(created_at, comment_id)`를 다음 조건에 넘깁니다. 예를 들어 `WHERE (created_at, comment_id) > (:lastCreatedAt, :lastId)`처럼 범위를 잡습니다.

Index seek는 인덱스의 시작 위치를 찾아 그 지점부터 필요한 방향으로 읽는 방식입니다. offset은 앞의 행을 세어 버려야 하지만 seek는 커서 위치로 바로 이동하므로 중간·마지막 페이지에서도 같은 원리로 동작합니다. 다만 현재 인덱스에 `created_at`이 없으면 인덱스로 후보를 찾은 뒤 별도 정렬이 필요합니다. 따라서 Cursor라고 해서 모든 비용이 사라지는 것은 아닙니다.

### Seed와 현재 Seed 구현

Seed는 테스트·벤치마크용 데이터를 일정한 규칙으로 채우는 초기 데이터 생성기입니다. 고정 random seed를 사용하면 매번 같은 게시글·댓글 분포를 재현할 수 있습니다.

현재 SQL은 `database/benchmark/seed-template.sql`을 기준으로 게시글 100개, 루트·대댓글, 익명 유형, Soft Delete를 생성하고, `seed-1k.sql`·`seed-10k.sql`·`seed-100k.sql`·`seed-1m.sql`이 대상 규모를 지정합니다. Java 하네스는 `JdbcTemplate.batchUpdate`로 같은 목적의 데이터를 넣으며 `BENCHMARK_COMMENTS`, `BENCHMARK_SEED` 환경변수로 규모와 seed를 바꿉니다. `test` 또는 `benchmark` 스키마가 아니면 실행을 중단하도록 되어 있습니다.

### Spring Profile과 현재 구성

Spring Profile은 환경별 Bean·설정 파일을 선택하는 기능입니다. 개발·테스트·운영 설정을 분리해 테스트 데이터 초기화가 운영에 섞이지 않도록 할 때 사용합니다.

현재 벤치마크 테스트는 `@ActiveProfiles({"test", "benchmark"})`를 사용하고 `application-test.yml`과 `application-benchmark.yml`을 읽습니다. 기본 URL은 `snowthing_test`이며, `SNOWTHING_TEST_DB_URL` 등이 있으면 환경변수 값이 우선합니다. `DataInitializer`는 `@Profile("local")`이라 테스트·benchmark 프로필에서는 실행되지 않습니다. SQL 파일을 MySQL CLI에서 직접 실행할 때는 Spring Profile이 관여하지 않으므로 Seed 시작부에서 현재 DB 이름에 `test` 또는 `benchmark`가 포함되는지 검사하고, 아니면 MySQL `SIGNAL`로 즉시 중단합니다.

### JDBC batch, JdbcTemplate.batchUpdate, SQL bulk insert

- **JDBC batch**: 여러 INSERT 파라미터를 JDBC 드라이버에 묶어 보내 네트워크 왕복과 파싱 횟수를 줄이는 방식입니다.
- **`JdbcTemplate.batchUpdate`**: Spring이 JDBC batch 처리를 감싼 API입니다. 배치 크기, 파라미터 바인딩, 예외 처리를 코드로 관리하기 쉽습니다.
- **SQL bulk insert**: 하나의 SQL에 여러 행을 넣거나 저장 프로시저·루프로 DB 안에서 생성하는 방식입니다. 애플리케이션 왕복은 가장 적지만 SQL이 DB 방언과 세션 상태에 강하게 묶입니다.

이번 벤치마크는 대량 생성이 목적이므로 JDBC batch와 SQL bulk insert를 우선 검토했습니다. 데이터 생성 시간을 조회 시간과 분리해 기록해야 하며, 생성 편의만 보고 JPA를 선택하면 측정 결과에 ORM 비용이 섞입니다.

### JPA `save()` 반복의 비용

`save()`를 10만 번 반복하면 엔티티 관리, dirty checking, SQL 생성, flush, 네트워크 왕복이 누적됩니다. batch size 설정과 `flush/clear`를 사용해 완화할 수 있지만, 대량 Seed에는 JDBC batch나 SQL bulk insert보다 느리고 메모리 사용도 커집니다. JPA를 선택할 이유는 도메인 콜백·검증·관계 매핑을 그대로 재사용해야 할 때이며, 순수 벤치마크 데이터 주입에는 적합하지 않습니다.

### 선택된 index와 key length

선택된 index는 실제 실행계획에서 MySQL이 사용한 인덱스입니다. `key_len`은 해당 인덱스에서 실제로 사용한 바이트 길이로, 복합 인덱스의 앞쪽 컬럼이 어디까지 조건에 활용됐는지 추정하는 단서입니다. key length가 짧다고 무조건 나쁜 것은 아니지만, 기대한 복합 인덱스 컬럼까지 사용되지 않았다면 WHERE 조건과 컬럼 순서를 다시 확인해야 합니다.

### actual loops, filesort, temporary table

- `actual loops`: 해당 실행 단계가 실제로 반복된 횟수입니다. LATERAL·Nested Loop에서 루트마다 자식 조회를 반복하면 loops가 커질 수 있습니다.
- `filesort`: 반드시 디스크 파일을 뜻하지는 않습니다. ORDER BY를 인덱스 순서로 해결하지 못해 MySQL이 별도 정렬 알고리즘을 사용했다는 뜻입니다.
- `temporary table`: GROUP BY·DISTINCT·정렬·중간 결과를 위해 임시 테이블을 만든 것입니다. 메모리를 넘으면 디스크 임시 테이블이 되어 비용이 더 커질 수 있습니다.

## 3. 이번 측정 결과에 대한 답변

### 1천건에서 보이지 않던 변화가 10만건에서 나타났나?

나타났습니다. 루트 첫 페이지 평균은 1천건 0.332ms에서 10만건 2.606ms, 백만건 36.578ms로 증가했습니다. 인덱스를 제거하면 후보 행과 정렬 대상이 크게 늘어 대규모에서 차이가 확실해졌습니다. 반면 루트 마지막 페이지는 인덱스 범위가 잘 줄어 1천건 0.315ms, 백만건 0.449ms로 변화가 작았습니다.

### `post_id`와 `parent_id` 선택도가 미친 영향

루트 조회는 `post_id`와 `parent_id IS NULL`을 함께 사용해 후보를 줄였고 `idx_comment_post_parent_id`를 선택했습니다. 대댓글 조회와 활성 대댓글 count는 `parent_id`와 `is_deleted`를 함께 사용해 `idx_comment_parent_deleted_id`를 선택했습니다. Hotspot에서는 한 parent에 행이 몰려 후보 수가 늘지만, parent 조건으로 전체 댓글을 읽는 상황은 피했습니다.

### estimated rows와 actual rows 차이가 큰 쿼리

인덱스 제거 루트 첫 페이지가 대표적입니다. 1M에서 예상 행은 약 347,250개였고 실제 처리 행은 200,001개였습니다. 인덱스가 없으니 통계상 넓은 범위를 읽는 계획을 세웠고, 실제 조건과 분포가 예상과 달라 차이가 났습니다. 차이가 있다고 해서 결과가 틀린 것은 아니지만, 잘못된 추정은 조인 순서와 인덱스 선택을 바꿀 수 있습니다.

### 복합 인덱스 컬럼 순서가 실제로 활용됐나?

현재 `(post_id, parent_id, comment_id)`는 WHERE의 `post_id`, `parent_id`를 활용했고, `comment_id`는 안정적인 범위·정렬 보조 역할을 했습니다. 하지만 ORDER BY의 `created_at`이 인덱스에 없어 모든 정렬을 없애지는 못했습니다. `(post_id, parent_id, created_at, comment_id)` 후보를 별도 비교해야 최종적으로 정렬 비용까지 줄었는지 판단할 수 있습니다.

### Hotspot에서 읽은 row가 증가한 이유

특정 루트에 대댓글이 집중되어 `parent_id` 조건 하나가 반환하는 후보가 일반 루트보다 많기 때문입니다. Top-5 LIMIT은 최종 반환량을 5개로 제한하지만, 현재 인덱스 순서와 삭제 조건에 따라 정렬 전 후보를 더 읽을 수 있습니다. 이것이 “응답은 작지만 읽은 row는 많을 수 있는” 이유입니다.

### Cursor가 중간·마지막에서도 index seek를 유지하나?

원리상 유지합니다. 커서 값이 `(created_at, comment_id)` 범위 조건으로 들어가므로 offset처럼 앞 페이지를 버리지 않습니다. 다만 현재 인덱스에 `created_at`이 없어 후보를 인덱스로 찾은 뒤 정렬하는 구간은 남습니다. 실행계획에서 range/index lookup과 정렬 단계를 함께 확인해야 합니다.

### 현재 인덱스가 쓰기 비용을 감수할 가치가 있나?

현재 결과에서는 가치가 있습니다. 인덱스는 INSERT·UPDATE·DELETE 때 추가 B-Tree 갱신과 저장 공간을 요구하지만, 루트 첫·중간 페이지와 Hotspot 조회에서 전체 스캔과 대규모 정렬을 피했습니다. 쓰기 비중이 매우 높은 서비스라면 인덱스 수를 줄이고 실제 읽기 빈도·p95·쓰기 지연을 함께 측정해야 합니다.

## 4. 자주 생기는 오해와 판단 기준

### 빠른 Full Scan이면 좋은 실행계획인가?

작은 테이블에서는 그럴 수 있습니다. 인덱스를 타면 인덱스 탐색 후 테이블을 다시 읽는 비용이 생기므로, 전체 행을 한 번에 읽는 Full Scan이 더 쌀 수 있습니다. 중요한 것은 “인덱스를 사용했는가”가 아니라 예상·실제 처리량, 응답시간, 데이터가 커질 때의 증가율입니다.

### estimated rows와 actual rows 차이가 크면 무엇을 하나?

먼저 `ANALYZE TABLE`을 실행하고 통계 갱신 여부를 확인합니다. 그래도 차이가 크면 데이터 분포가 치우쳤는지, 조건 컬럼 상관관계가 있는지, 히스토그램이나 복합 인덱스가 필요한지 검토합니다. 쿼리 구조를 바꾸기 전 실제 `EXPLAIN ANALYZE` 원문과 운영과 유사한 데이터로 재현해야 합니다.

### 10만건 결과가 운영 트래픽을 보장하지 않는 이유

행 수는 저장 데이터의 한 축일 뿐입니다. 운영에서는 동시 사용자 수, 게시글별 쏠림, 캐시 적중률, 디스크·버퍼 풀 상태, 쓰기와 읽기 경합, 네트워크 응답 크기가 함께 작용합니다. 따라서 이번 결과는 인덱스와 쿼리 구조의 기준선이지, 운영 p95를 보장하는 부하 테스트 결과가 아닙니다.

### Seed 분포를 이렇게 고른 이유

게시글 100개는 `post_id` 선택도를 관찰할 최소한의 비교군입니다. 일반 게시글은 넓게 분산하고, 중간 게시글과 Hot post는 점진적으로 집중도를 높였습니다. 루트와 대댓글, 삭제 행, 동일 `created_at`, 작성자 유형을 섞어 실제 조회 조건과 정렬 tie-breaker를 재현했습니다. 고정 seed는 같은 조건의 인덱스 전후 비교를 가능하게 합니다.

## 5. 현재 구조에서 더 커졌을 때의 대응

### 데이터가 정말 많아지면

1. `(post_id, parent_id, created_at, comment_id)`와 `(parent_id, is_deleted, created_at, comment_id)` 후보를 실제 workload로 비교합니다.
2. `ANALYZE TABLE` 자동화와 slow query·p95 모니터링을 붙입니다.
3. 게시글 또는 기간 기준 파티셔닝은 삭제·보관 정책과 함께 검토합니다. 파티션 키가 쿼리 조건과 맞지 않으면 오히려 이점이 없습니다.
4. 오래된 댓글은 읽기 전용 보관 테이블이나 아카이브 저장소로 분리하고, 현재 게시글 조회 테이블의 working set을 줄입니다.
5. 단일 Hotspot이 계속 커지면 댓글 목록 캐시와 비동기 count 집계를 검토하되, 댓글 생성 직후 정합성 요구와 캐시 무효화 비용을 먼저 정합니다.

### 유저가 정말 많아지면

1. DB 커넥션 풀과 애플리케이션 스레드 풀을 무작정 늘리지 말고 p95·DB CPU·lock wait를 기준으로 상한을 정합니다.
2. 읽기 트래픽은 읽기 전용 Replica로 분산할 수 있지만, 생성 직후 조회의 read-after-write 요구가 있으면 주 DB 라우팅이 필요합니다.
3. 게시글별 Hotspot과 사용자별 요청 빈도에 rate limit을 적용하고, 익명 비밀번호 검증에는 Redis 기반 시도 제한을 도입합니다.
4. 댓글 목록·Top-5 preview는 짧은 TTL 캐시를 사용할 수 있으나 생성·수정·삭제 시 정확한 무효화가 필요합니다.
5. 단일 게시글이 모든 트래픽을 받는 경우 게시글 단위 캐시 키 분산, 큐 기반 count 갱신, 필요 시 샤딩을 검토합니다. 샤딩은 ID·트랜잭션·조인 경계를 바꾸는 큰 비용이 있으므로 Replica와 캐시로 해결되지 않을 때 선택합니다.
