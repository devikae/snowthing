# API Design Skill

## 기본 원칙

- API 계약은 구현 세부사항이 아니라 외부 클라이언트와의 명시적인 계약으로 취급한다.
- Entity를 API 스펙으로 사용하지 않는다.
- 요청 DTO와 응답 DTO의 책임을 분리한다.
- URL은 가능한 한 리소스 중심으로 설계하고 HTTP Method 의미를 맞춘다.
- 성공/실패 응답 구조와 오류 코드를 프로젝트 전체에서 일관되게 유지한다.
- 필드 이름, nullable 여부, enum 값, 날짜 형식, pagination 방식이 기존 명세와 일치하는지 확인한다.

## HTTP 의미

- GET: 조회이며 서버 상태를 변경하지 않는다.
- POST: 생성 또는 명령성 작업에 사용한다.
- PUT: 전체 교체 의미가 적절할 때 사용한다.
- PATCH: 부분 수정에 사용한다.
- DELETE: 삭제 또는 삭제 상태 전환에 사용한다.
- 상태 코드는 단순히 200으로 통일하지 않고 의미에 맞게 사용한다.

## 호환성

- 기존 클라이언트가 사용하는 필드 삭제/타입 변경/의미 변경은 Breaking Change로 취급한다.
- 응답 필드 추가는 대체로 호환 가능하지만 클라이언트의 엄격한 스키마 검증 여부를 확인한다.
- enum 값 추가도 클라이언트가 exhaustive switch를 사용하는 경우 영향을 줄 수 있음을 고려한다.

## 목록 API

- 정렬 기준은 결정적이어야 한다.
- 동일 정렬 값이 존재할 수 있다면 tie-breaker를 둔다.
- OFFSET, Cursor, Keyset 방식의 Trade-off를 데이터 규모와 UX 기준으로 비교한다.
- 필터 조건과 정렬 조건이 인덱스를 활용할 수 있는지 확인한다.

## Idempotency

결제, 주문, 포인트 지급, 외부 API 재시도 등 중복 요청이 문제를 일으킬 수 있는 작업은 Idempotency Key, Unique Constraint, 상태 머신 등의 방식을 검토한다.

## 금지

- 내부 Exception 메시지를 그대로 API 응답으로 노출하지 않는다.
- DB 컬럼명을 그대로 외부 계약으로 노출하는 것을 당연하게 여기지 않는다.
- 민감정보를 응답 DTO에 포함하지 않는다.
