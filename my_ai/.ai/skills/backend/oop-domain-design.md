# OOP & Domain Design Skill

## 목적

객체지향 원칙을 기계적으로 적용하는 것이 아니라, 변경 이유와 책임을 기준으로 객체를 설계한다.

## 핵심 규칙

- 클래스는 하나의 명확한 책임과 변경 이유를 갖도록 설계한다.
- 데이터와 그 데이터를 다루는 핵심 규칙이 항상 함께 움직인다면 가능한 한 같은 객체에 둔다.
- 모든 로직을 Service에 몰아넣는 Transaction Script 형태를 습관적으로 만들지 않는다.
- 반대로 단순 CRUD까지 무리하게 도메인 객체로 추상화하지 않는다.
- 상속보다 합성을 우선 검토한다.
- 인터페이스는 실제로 교체 가능성이 있거나 경계를 만들 이유가 있을 때 도입한다.
- 구현체가 하나뿐이고 변경 가능성도 없는 단순 코드에 인터페이스를 습관적으로 만들지 않는다.
- SOLID는 규칙 암기가 아니라 결합도와 변경 비용을 줄이기 위한 판단 기준으로 사용한다.
- 도메인 객체가 자신의 상태 규칙을 스스로 보장할 수 있다면 외부에서 Setter로 상태를 무제한 변경하지 못하게 한다.
- 의미 없는 Getter/Setter만 가진 빈약한 도메인 모델을 경계한다.
- Enum으로 표현할 수 있는 유한한 상태를 문자열로 관리하지 않는다.
- 상태 전이가 존재하면 허용 가능한 전이를 명시적으로 설계한다.

## 객체 생성

- 생성 시 반드시 유효해야 하는 값은 생성자 또는 정적 팩터리에서 검증한다.
- 필수 값 누락 상태의 객체가 만들어진 뒤 나중에 Setter로 완성되는 구조를 피한다.
- 생성 로직이 복잡하면 정적 팩터리 또는 별도 Factory를 검토하되, 필요 없는 추상화는 만들지 않는다.

## 의존성 방향

- 상위 정책이 하위 구현 세부사항에 강하게 묶이지 않도록 한다.
- 도메인 로직이 HTTP, Servlet, DB Driver, 특정 프레임워크 객체에 직접 의존하지 않도록 한다.
- 기술 세부사항을 도메인 핵심으로 끌어들이지 않는다.

## 피해야 할 패턴

- God Class / God Service
- 무분별한 Utility Class
- static 전역 상태
- 의미 없는 Wrapper Class
- 실제 대체 가능성이 없는 인터페이스 남발
- 모든 필드 public Setter
- String, int 등 primitive 값만으로 모든 도메인 의미를 표현하는 Primitive Obsession

## 설명/설계 시 반드시 검토

1. 객체의 책임
2. 객체가 보장해야 하는 불변식
3. 변경 가능성이 높은 지점
4. 객체 간 결합도
5. 상속과 합성 중 어떤 방식이 적절한지
6. 도메인 로직과 애플리케이션 흐름 로직의 경계
7. 테스트 가능성
